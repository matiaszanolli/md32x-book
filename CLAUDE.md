# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An mdBook (pinned to 0.4.40) technical reference for the Sega Mega Drive/Genesis, the 32X and the Hitachi SH-2 (SH7604). It is prose, not code: the only program is `tools/check.py`, apart from small example ROMs under `src/howto/` (e.g. `src/howto/32x-hello/`), which chapters pull in with mdBook's `{{#include file:anchor}}` and `ANCHOR:` comment markers, so the listing on the page is the code that was built and tested. Their build scripts copy Sega's initial program (`$3F0-$7FF`) from a cartridge dump at build time; never commit it. Most chapter pages are still outlines (`> **Status:** outline only.` with a `## To write` checklist, `## Open questions` and `## Sources`); filling them in is the main work.

## Commands

```sh
mdbook serve --open                  # live preview at http://localhost:3000
mdbook build                         # output in book/ (gitignored)
python3 tools/check.py               # links, anchors and citation keys; exit 1 on failure
python3 tools/check.py --verbatim    # also flags 12+ identical words in a row copied from sources/
```

CI (`.github/workflows/deploy.yml`) runs `tools/check.py` then `mdbook build` on every push and PR, and deploys to GitHub Pages from `main`. `--verbatim` is not run in CI because `sources/` (local copies of the original manuals, as `.md`/`.txt`) is not committed.

## How the pieces fit

- `src/SUMMARY.md` is the table of contents and the only thing that makes a page part of the book. `create-missing = false` in `book.toml`, so a SUMMARY entry pointing at a missing file fails the build; a new page needs both the file and its SUMMARY line.
- Parts map to directories: `megadrive/` (I), `sh2/` (II), `32x/` (III), `howto/` (IV), `patterns/` (V), `techniques/` (VI, algorithms: fixed point, software 3D, first-person, roads, voxels, 2D effects, text, compression, memory, game logic, asset pipelines), `appendices/`.
- **Citations**: any bracketed uppercase key not followed by `(`, e.g. `[SH7604 §8.3]` or `[32X-HWM p.42]`, must match a `### KEY` heading in `src/appendices/bibliography.md` (compared via the lowercased heading anchor). Add new sources there first. Fenced code blocks are skipped by the checker, but inline text like `[ABC]` outside code will be treated as a citation.
- **Links**: relative `.md` links and `#anchors` are validated; anchors are computed from headings the same way mdBook does (lowercase, punctuation stripped, spaces to `-`), so renaming a heading can break links elsewhere.
- **Confidence tags**: claims that affect working code get `<span class="tag tested|manual|emulator|disputed">…</span>`, styled by `theme/tags.css` and defined in `src/conventions.md`. `tested` needs the console model (and a test ROM link if one exists). `disputed` claims also get a row in `src/appendices/discrepancies.md`, linked from where the claim appears.

## Reference projects

Three sibling repos by the author are the book's worked examples and the source of its original research. Read them for measurements and real code, and cite them by their bibliography keys:

| Key | Local path | What it is |
|-----|------------|------------|
| `VRD-NOTES` | `../32x-playground` | Virtua Racing Deluxe: disassembly plus the 60 fps (VR60) rework. There is no `main` branch: for the original game and `patterns/case-study-vr.md`, read the **`master`** branch (its `disasm/sections/` and `analysis/` docs, March 2026) with `git show master:PATH` or `git archive master`, never by checking it out (the working tree is on `60fps_project` with uncommitted changes). Use the VR60 work only for which results the project later retracted (`README`, `KNOWN_ISSUES`, `VR60_STATUS.md`). `master` builds a modified ROM and its README's "40 FPS achieved" is retracted; its docs mix original and modified builds and contradict each other on which SH-2 renders. Basis of the introduction and `patterns/case-study-vr.md`. |
| `AB-DISASM` | `../aerobiz-disasm` | Aerobiz Supersonic (Mega Drive): byte-identical disassembly of the original 1 MB game. The plain Mega Drive reference: header, Sega's MD initial program at `$200`, VDP, Z80 sound, save RAM. The original ROM is in the folder. |
| `AU-NOTES` | `../aerobiz-ultimate` | Aerobiz Ultimate: 32X remaster of Aerobiz Supersonic, forked from `../aerobiz-disasm`. `PORT_ARCHITECTURE.md` is the design of record; `HARDWARE_TESTS.md` lists what still needs a real console; `ROADMAP.md` separates what ships from what is only demonstrated. Basis of `patterns/case-study-aerobiz.md`, the book's worked example of porting a Mega Drive game to the 32X: read it against `AB-DISASM`, the original's source. |

Both `Virtua Racing Deluxe (USA).32x` copies (in `../32x-playground` and `../aerobiz-ultimate/reference/` (a symlink to the first)) are **not the retail original**. They have MD5 `85eda196…`, not the `72b1ad0f…` the VRD README gives, their header checksum does not match, and the SH-2 program contains code injected by the project's own tools: the Master's interrupt handler at `0x060006A4` is overwritten with the `REDY`/`WORK`/`DONE` words from `tools/inject_master_sync.py`. The project's "byte-identical" disassembly was matched to this patched file, so it does not prove originality either. Only the first 2 KB (headers, Sega's initial program) is trusted. Do not cite the game's own code past that as evidence of what Sega shipped. Confirm it against a clean retail ROM, or cite the project's documents as the project's description. A clean retail copy now exists: `/home/matias/Downloads/Sega-32x-Romset-us/Virtua Racing Deluxe (USA).32x` (MD5 `72b1ad0f…`, checksum `$1E4D` matches), part of a US romset of 29 retail cartridges supplied on 6 October 2026 (bibliography `32X-ROMSET`, MD5 list in `notes/games/romset-us.md`; not committed). Read VRD's code from that file. Compared byte for byte, the patched copy differs from it only in 103 bytes at `$020650`-`$0206BD`, but `master`'s disassembly source has further project changes (e.g. the Slave's code from `$020608`, commit `d8b770c`), so cite the retail file, not the source.

`SWA` is the clean retail reference: `../32x-playground/Star Wars Arcade (USA).32x` (MD5 `ae3a42c6…`, header checksum matches). Its SH-2 program is `0x548C` bytes from ROM `$854`, loaded to `0x06000000`, with Master/Slave vector tables at `0x06000000`/`0x06000200`. Disassemble it with capstone (`CS_ARCH_SH`, `CS_MODE_SH2 | CS_MODE_BIG_ENDIAN`). Don't name a helper script `dis.py`, which shadows Python's standard library. capstone's SH-2 mode also decodes 452 SH-2A/SH-4A-only words (`movml.l`, `jsr/n`, `divu`…); `sh-elf-objdump -b binary -m sh2 -EB` decodes exactly the SH-2's 142 instructions. It confirms Sega's VRES handler (including the sample's slip: `$44E0` goes into the pointer register, so 0 is written to `0x000044E0` and CHCR0 stays 0), two-way cache mode with code at `0xC0000000`, the single-entry interrupt dispatcher with the TOCR flip, and the PSG note table shared with VRD. It runs headless the same way as MK2 (below); in play it keeps PRI = 0 with no through bits, and its cockpit and score are Mega Drive tiles. Its split is a two-stage pipeline: the Master transforms (`mac.l` + `xtrct`) and bucket-sorts polygons into double-buffered lists, the Slave draws them from on-chip RAM and also runs the PWM interrupt (see `src/patterns/cpu-split.md`). The on-chip routine (2 KB copied from cartridge `$005CE0`, disassemble it with `--adjust-vma=0xC0000000`) only cuts polygons into trapezoids; the Slave's watchdog interrupt (level 5, also in on-chip RAM at `0xC0000582`) draws them with auto fills paced by the timer (see `src/techniques/software-3d.md`).

`MK2` is a second clean retail reference, from an outside studio (Probe): `../32x-playground/Mortal Kombat II (Japan, USA).32x` (MD5 `a95c0e7c…`, header checksum `$4EB1` matches). SH-2 program `0x7E14` bytes from ROM `$978` to `0x06000000`; Master/Slave entries `0x06000240`/`0x06000244`, vector tables `0x06000000`/`0x06000120`. Disassemble with `sh-elf-objdump`; most of the program past `0x060051E2` is data (palettes, tables), so trace code from the entry points and dispatcher tables rather than reading straight through. Analysis notes are in `notes/games/mk2/`. Shared scripts for every retail ROM (disassembly, frame-buffer rendering, building and driving the headless PicoDrive frontend, with its profiler, watch log and save states) are in `notes/games/tools/` with a README; the scratchpad does not survive between sessions, so keep scripts there.

`AB32X` is a third clean retail reference, a Sega release: `../32x-playground/After Burner Complete ~ After Burner (Japan, USA).32x` (MD5 `ec952985…`, header checksum `$4174` matches). SH-2 program `0x1A000` bytes from ROM `$53000` to `0x06000000`; Slave entry/VBR `0x06000200`/`0x06000000`, Master `0x06002120`/`0x06002000`. Its 68000 code runs at `$88xxxx` (cartridge offset `$xxxx`); its own cartridge vector table is ignored in 32X mode, the jump table at `$200` is what counts. Master draws (auto-fill horizon, scaled sprites with a decoded-sprite cache), Slave runs a 16-voice PWM mixer, the 68000 calls the Master once per object. Notes and the headless input generator are in `notes/games/ab/`; its scaler is in `src/techniques/2d-effects.md`, its sprite cache in `memory.md`, its RLE format in `compression.md` and its projection and bucket sort in `software-3d.md`.

`../32x-playground` also holds Sega's development discs and other dumps not all read yet. In the bibliography: `ECCO`, `RLT`, `GNU-SIERRA` (sample 1.2, the one sample whose SH-2 code runs from the cartridge), plus retail `MCX` and `CHAOTIX`. Chaotix's SH-2 program is `0x9000` bytes from ROM `$77800` to `0x06000000`; its Slave plays PWM from 1 KB of code copied from cartridge `$7FC00` into on-chip RAM. MCX's 68000 feeds PWM itself from its line interrupt. Chaotix is also the only retail game in the sources with save RAM (512 bytes at `$200001`, over its own ROM, switched through `$A130F1` with RV set) and so the only one that sets RV and runs TI item 8; its VRES handler reads RV correctly. The sound paths of all five retail games are summarised in `notes/games/mars/CATALOG.md`. `EGYPT` and `MARS-CHECK` (a hardware diagnostic, checksum `$8DA0` matches; its test harness, command map and register, interrupt-count, FIFO and fill tests are decoded in `notes/games/mars/CATALOG.md`; the SH-2-side VDP and frame buffer tests are not) are in the bibliography too. `SOJ` and `TEXTURE` (*Texture Test*) are in the bibliography too, but only their headers, jump tables and initial programs have been read. Files tagged `[b1]`/`[b2]` are damaged dumps; don't use them. `notes/games/tools/header32x.py *.32x` summarises every header and user header in one run. `Gens_KMod_v0.7.3` (a debugging emulator) is also in that folder.

`S32X-SKILL` (haroldo-ok's sega-32x-gamedev Claude skill, cloned for reading only; its text is copied to `sources/s32x-skill/` for the verbatim check) is a secondary source of homebrew practice: COMM slot discipline, PWM safe range (~2..1032), the GCC 12.1 SH-2 miscompile traps, 6-button pad mirroring in emulators, SRAM save formats, `SEGA SSF` mapper selection. Its claims are mostly PicoDrive-verified: cite it for pitfalls and patterns, tag hardware claims from it `emulator`, and prefer a manual or ROM evidence where one exists. Useful for the PWM, communication, toolchain, profiling, I/O and Part V chapters.

Neither 32X project has been run on a real 32X yet (both use PicoDrive, Aerobiz Ultimate also Ares), so claims drawn from them get `emulator`, not `tested`. Check the project's status docs before repeating a result; VRD's README marks some earlier findings as invalidated.

`../aerobiz-ultimate/docs/*.md` holds converted text of most manuals in the bibliography. Copying them into `sources/` is what enables `tools/check.py --verbatim`. The conversions contain errors (wrong numbers, a dropped digit, garbled tables), so check any disputed value against the original scan in the same folder. Known example: `32x-technical-info.md` files item 8's bank chip listing under item 10. Both transcriptions of 32X-HWM §5.1 (ours and 32XDK's) flatten the boot flowcharts (Figures 5.2-5.3, pp.82-83) into lists that give the Slave and the Master's CD path a checksum step the scan does not have. `genesis-32x-overview.md` inverts the PRI/through-bit list under the priority figure (scan p.49 agrees with 32X-HWM). `sh7604-hardware-manual.md`'s register summary (around line 8350) puts the division unit at `H'FFFFFE00`-`FE14`, the SCI's addresses; its §10 table and the PDF give `H'FFFFFF00`-`FF14`. The 32XDK devkit publishes its own transcriptions of the 32X Hardware Manual, the 32X H/W Information, SH-PM and SH7604 (copied to `sources/32xdk/`); they differ in places from the Aerobiz Ultimate copies, and 32XDK's 32X Hardware Manual has the bitmap mode register bits wrong (PRI/240 at 13/7; the scan says 7/6). 32XDK's SH-PM has three opcode-table errors (`MOV #imm`, `MOV.L @(disp,Rn)` missing × 4, `SWAP.B/W`); its SH7604 and H/W Information match ours except for the tables of contents. Cite the manual's key, not the transcription. Emulator behaviour is cited as `PICODRIVE`; the VRD project's RV and timing patches to its PicoDrive copy stay under `VRD-NOTES`. Most PDFs are images with no text layer: render a page with `pdftoppm -r 150 -f N -l N -png` and read it. In `32XUSHardwareManual.pdf` (32X-HWM) printed pages 65, 70, 72 and 80 are missing from the scan, so printed page *n* is PDF page *n* + 2 up to p.64, *n* + 1 for pp.66-69, *n* for p.71, *n* − 1 for pp.73-79 and *n* − 2 from p.81; and in `Genesis32XUSOverview.pdf` (32X-OV) *n* + 1; the 32X-HWM text copy marks some register bits writable that the scan shows read only (e.g. ADEN at `0x20004000`), so check register R/W columns on the scan. The text copy also numbers chapter 4 differently: its §3.4-3.6 (block access by SH-2, 68000, Z80) and §4.1 (access timing) are the scan's §4.1-4.3 and §4.4 (pp.73-78). Cite the scan's numbers; older chapters still cite some of these as §3.4. `GenesisTechnicalOverview.pdf` (MD-TO) `SH-1_SH-2_CPU_Core_Architecture.pdf` (SH-PM, printed page + 4) and `SH7604_Hardware_Manual.pdf` (printed page + 16) do have one, so `pdftotext -f N -l N` finds pages fast. MD-SWM's scan is `../32x-playground/docs/SegaGenesisSoftwareManual_1990-02-06.pdf` (OCR text layer; printed page = PDF page − 3 in the main manual, and the bound-in sound manual restarts its numbering). Its text copy (`sega-genesis-software-manual.md`) mistranscribes the VDP register pages and the sprite link field, so check bit layouts on the scan, MD-TO pp.22-26, GENVDP or PicoDrive. Retail ROMs and BIOS dumps in the two projects count as evidence for what hardware does. Record anything the scans, the ROMs and the emulators disagree on in `src/appendices/discrepancies.md`.

## Technique catalogue (`notes/`)

`notes/techniques/` is working material, not part of the book (mdBook only builds `src/`, and `tools/check.py` does not check it). `by-chapter/` holds every algorithm and hardware technique harvested from the sources, one file per target chapter (`32x__vdp.md` = `src/32x/vdp.md`; `new/*.md` = proposed chapters), each entry with source file:line, explanation, numbers and evidence level. `raw/` keeps the original agent reports with each source's caveats (known bugs in S32X-SKILL's `r3d.c`, misleading labels in AB-DISASM, findings the VRD project later invalidated, d32xr build flags that disable features). Outline pages link their catalogue file in "To write" as a plain path, not a Markdown link, because `notes/` is not published. When writing a chapter, work through its catalogue, verify each claim against its source, re-cite with the bibliography key, and keep the evidence level as the tag.

## Writing rules (from CONTRIBUTING.md)

1. Original wording only. Never paste text from Sega, Hitachi or Motorola manuals or other people's docs. Register layouts, addresses, bit meanings and timings are facts and can go in tables; explanations must be our own.
2. Cite everything that affects code, with section/page when known.
3. Tag how we know (see above).

Style: plain words over jargon; explain a term on first use and add it to `src/appendices/glossary.md`; prefer tables for register bits. Hex is `$A15100` for 68000 addresses and `0x20004000` for SH-2 addresses; KB = 1024 bytes, chip capacities in Mbit.
