# Virtua Fighter (32X, Sega AM2, 1995): the 68000 side

Working notes, not part of the book. ROM: `Virtua Fighter (Japan, USA).32x`, 4 MB, serial GM MK-84701-00, header checksum `$1951` matches (MD5 `901e97c9…`). The SH-2 program (cartridge `$100000`, `$22000` bytes) is read in `SH2.md`; this file covers only what the 68000 does and what it says to the SH-2s. Addresses `$xxxxxx` are 68000 addresses, `0x0600xxxx` are SH-2 addresses; "cart $xxxxxx" is a cartridge file offset. The 68000 sees cartridge offset *n* at `$880000+n` (first 512 KB) and, with bank 0 selected, at `$900000+n` (first 1 MB).

## 0. How this was read, and how far to trust it

| Source of a statement | Tag used below |
|---|---|
| Disassembly of the retail ROM (GNU objdump `m68k:68000`, `vfdis.py`) | **code** |
| A headless PicoDrive run (3,600-frame attract run with no input, and a 5,000-frame run with scripted Start/button input, `inp1.csv`), with a log of every 68000 access to `$A15100-$A151FF` (frame, PC, size, value, cycle within the frame), of every VDP register write and DMA, and of Z80/YM2612 writes | **emulator** |
| My inference from the two | **inference** |

PicoDrive charges the SH-2s no memory wait states, so every time and ratio below that involves an SH-2 is an emulator figure and says nothing about a console. Times for the 68000's own code are instruction-table arithmetic checked against the emulator's cycle counter.

The PicoDrive PC profiler (`VRD_PROFILE_PC`) is **not used** for the 68000's load: it attributes 65-88% of the run to the wait loop at `$FF1234`, while the event log shows that loop running for about 8% of a picture (§2.4). PicoDrive's poll detection puts sleeping time on the last polled PC. The profile is still useful as a list of which PCs ever executed.

Two things the emulator patches that look like game behaviour but are not: PicoDrive's idle-loop detection rewrites the opcode of a `bne` in 68000 RAM from `$66` to `$73`/`$71` (offsets `$1C`, `$58`, `$774`, `$100C`, `$104E`, `$1234`, `$1C74`, `$1C9E`, `$1CD0` of the RAM image), so RAM dumps taken from the emulator must be compared with the cartridge copy before being disassembled. The cartridge copy (`$89A23E`) is the clean one.

Helper scripts (all in this directory, all read-only with respect to the ROM and the other repos): `vfdis.py` (68000 disassembly by 68000 address, `VFROM=` selects another ROM), `ramdump.py` / `framewatch.py` (68000 RAM at chosen or every frame through the debugger), `patch_m68klog.py` / `patch_vdplog.py` / `patch_z80log.py` (patches for a PicoDrive copy; see the header of each), `logsum.py`, `msgs.py`, `picturetime.py` (summaries of those logs), `mdplanes.py` (render Mega Drive planes from a VRAM dump), `hufftile.py`, `kosdec.py` (Python ports of the game's two decompressors, verified, §1.6), `blockmap.py` (entropy map of a ROM), `dmasum.py`, `statetrace.py`, `build_vf68_core.sh`. Small outputs of these for the runs described are in `data/`. Rebuild recipe: §10.

## Most important findings

1. **The 68000 is an I/O, presentation and sound processor. It runs no fight engine.** In a played fight it reads the pads, sends two pad bytes and a command word to the Master, waits, reads about 28 bytes back, and draws a HUD; in the attract fights it sends no input at all. The fight itself, including both fighters in the attract mode, is on the SH-2s. Per picture the 68000 sends at most 5 bytes of data (two pad bytes, a replay flag, two sound bytes) plus the command; the SH-2s answer with up to 4 status bytes in COMM (COMM7, COMM2) and 24-28 bytes in the frame buffer. No joint angles, matrices or polygon lists cross; the 68000 holds no model, motion or collision data. (§4, §5)
2. **One picture is two vertical blanks, two 68000 states.** State A (after the "go"): sound request to the Master, clear the back buffer with 240 auto fills, hand the frame buffer to the SH-2s (FM = 1). State B (next blank): wait for COMM0's high byte to read 0, take FM back, copy the mailbox from the frame buffer at `$840200`, flip FS. The "go" itself, `COMM0 = $0186` (or `$0184` in play) plus a CMD interrupt to the Master, is written by the **vertical-blank handler**. In PicoDrive the attract fights run at exactly 30 pictures a second (901 pictures in 1,801 frames), the SH-2s take 1.2-1.8 frames of the 2-frame window (the short end is censored), and one picture in 1,101 of a played fight ran to three blanks. (§2)
3. **Main loop and vertical-blank handler live in work RAM**, copied from cartridge `$89A23E` (`$2BBC` bytes) to `$FF0000` at boot. The current state is the operand of a `jsr` at `$FF0002`; the blank-time task is the operand of another `jsr` at `$FF0038`; both are rewritten by state code. The sound driver is called at the end of every blank. This is the same loop shape as Virtua Racing Deluxe's (`jsr state; flag; wait for the interrupt to clear it`), with different details (§7).
4. **The sound is Sega's driver V3 ("V313F [PCM NO USE] VF1")**, copied to RAM `$FF4000` (`$1D16` bytes from cart `$0E0000`), with its work area at `$FF5D16`. The Z80 is parked on a 6-byte loop (`DI; DI; JR $`). The driver copies each music's data into **Z80 RAM** (4,880 bytes at the start of the fight music) and reads it from there. FM and PSG are written by the 68000. The 32X PWM is never touched by the 68000: its requests (two bytes) are forwarded to the Master, as command 8 in fights and command 2 in menus, and the Slave plays the voices (`SH2.md`). (§6)
5. **Communication uses COMM0 two ways.** *Simple commands* (`$01`-`$0E`, `$10`): wait for COMM0's low byte (`$A15121`) to read 0, write the command to that byte alone, raise CMD (`$A15103 = 1`, the Master only), wait for the byte to read 0 again. *Picture commands* (`$0182`-`$0186`, `$0188`-`$018D`): write the **word** `$01cc`, raise CMD, and later wait for the **high byte** (`$A15120`) to read 0. The low byte is cleared when the Master takes the command; the high byte stays 1 until the picture is finished, so sound commands can be sent while a picture is in progress. (§3)
6. **Never used after boot: the Slave's CMD interrupt (`INTS`), the DREQ FIFO, RV, the bank register, the `$A130F1` mapper, Mega Drive DMA from the cartridge, `$A1518A`, PWM registers.** Every one of 37,194 DMAs in the played run reads work RAM (register 23 = `$7F`). Bank 0 stays selected, so the 68000 can only ever read the first megabyte; cart `$100000-$3FFFFF` (the SH-2 image and everything after it) is invisible to it. (§3.7, §1.2)
7. **Compression, three schemes, all read and two verified by decoding with a port:** a Huffman coder of (pixel, run) symbols for Mega Drive tiles (`$880D10`; 35 blocks decode exactly to the byte where the next one starts, and two of them match the emulator's VRAM long for long); a Kosinski-style LZ for byte data and for 320×224 8-bit pictures written straight into the 32X frame buffer (`$881038`); a word-oriented tilemap compressor (`$880E50`, not verified). The pictures that the Master draws on command 5 (`$99D064`, `$9A0458`, `$9A0B3E`, `$9C7EDA`) are in the same LZ format. (§1.6)
8. **Compositing in fights:** 32X packed-pixel mode with PRI = 0; 246 of the 256 palette entries (all used ones except entry 0) have the through bit; the Mega Drive draws the sky and sea (plane B, 32 rows of 41 words re-sent by DMA every picture from a RAM panorama, window position from the camera value the SH-2s send back) and the HUD (plane A: life gauges, round marks, timer digits, names). The 68000 itself clears the 32X back buffer to index 0 each picture. (§5)
9. **A late picture slows the game, it does not skip.** The round timer (68000, BCD, 10 hundredths per three pictures) and the attract demo's length (900 pictures) are counted per picture, not per vertical blank. (§2.4, §4.3)
10. **The 68000 refuses PAL consoles** (`$A10001` bit 6): it prints "DEVELOPED FOR USE ONLY WITH NTSC GENESIS SYSTEMS AND NTSC MEGA DRIVE SYSTEMS." and divides by zero into the common hang stub. Static reading, not run. (§1.1)

## 1. Boot and memory map (question 1)

### 1.1 Boot sequence

The standard Sega initial program (IP) occupies `$0003F0-$0007FF`; the game's own code starts at `$880802`.

If not (first start): wait for `'M_OK'` in `$A15120` and `'S_OK'` in `$A15124`, compare `$A15128` (checksum posted by the Master BIOS, `$1951` here) with the header's `$18E`, clear `$A15120-$A15127`, set `$FF8008 = 'INIT'`, wait ~500 loops, then **the first command: `$A15121 = 9`, CMD to the Master**, wait for it to clear (frame 5) | code, emulator log |
| 4 | `$880A10` | read `$A10001`: `$8200 = $FF` if bit 7 (overseas), `$8201 = $FF` if bit 6 (PAL), `$8202 = version byte` | code |

| 12 | `$880B76` | load the font (`$96914C`, 45 tiles, 517 bytes packed → 1,440) to VRAM 0 and the first palette | code, verified |
| 13 | `$880A6E` | **PAL check** (§1.1 note) | code |
| 14 | `$8809F8` | `sf $8D00`, `jmp $FF0000`: the main loop starts (frame 5-6; the first state is `$88109E`, which only sets the next state `$892630`) | code, emulator |

PAL note: `btst`-style test of `$A10001` bit 6; if set, four lines of text are written through `$8951C6` and the code executes `divu.w #0,d0`, which vectors (entry 4 of the jump table) to the hang stub `$88088E`. Header region byte is `'5'` (Japan + USA). Not run.

**Reset button** (jump table entry 0, `$8808B4`): `btst #1,$A15101` (RES: are the SH-2s running?); if 0, a cold start through the IP's second stage (`$8806E4`); if 1 and `$FF8008 == 'INIT'`, wait for `'M_OK'`/`'S_OK'` again, clear them, and go to step 6 (re-init Z80 and everything after). **There is no `VRES` word anywhere in the 68000 code or in the cartridge** (a search for the ASCII string finds nothing in the 4 MB), unlike Virtua Racing Deluxe, After Burner Complete and Space Harrier.

### 1.2 Bank register and mapper

`$A15104` is written once, with 0, by the IP's register clear (`$880714`). **No `$A130F1` write exists anywhere** (a whole-ROM `a151scan.py` over `A130F0 A130F1 A15104` finds only the IP's clear), and none occurs in either run. So, on a 32 Mbit cartridge: bank 0 stays selected, `$900000-$9FFFFF` shows cart `$000000-$0FFFFF`, and **the 68000 can read only the first megabyte**. Every `$9xxxxx` pointer in the 68000 code and every pointer it hands to the SH-2s (`$99D064`, `$9A0458`, `$9A0B3E`, `$9C7EDA`, `$979BE8`, …) is cart offset `$0xxxxx`. The SH-2 image (`$100000-$121FFF`) and the 3 MB after it are read by the SH-2s only. This is the Mortal Kombat II arrangement (68000 pointers into the first megabyte at `$900000`, SH-2s read all of it) rather than After Burner's or Chaotix's bank switch. The SH-2s must convert the 68000 pointers (`$9xxxxx` → `0x02000000 + offset`, a difference of `0x01700000`, the constant the book gives for Mortal Kombat II): check in `SH2.md`.

### 1.5 Interrupts

Only level 6 (vertical blank) is ever taken. `SR = $2500` in the main loop, so levels 1-5 are masked; VDP register 0 is `$04` (no horizontal interrupt) and the VDP's HINT counter (register 10) is 7 but unused. Every other vector, including all exceptions and the 32X's level-3 interrupt, hangs in the stub.

### 1.6 The three decompressors

All three read from the cartridge and are used while the screen is black or faded (the long black stretches in the scene list, §2.3, are decompression time).

| Routine | Output | Scheme as read | Checked |
|---|---|---|---|
| `$880D10` (VDP port) / `$880D22` (RAM) | 4-bit tiles, 8 longs per tile, to `$C00000` or to `(a4)+` | Header word: bits 12-0 = number of tiles, bit 15 = XOR each output long with the previous one (the `$880DDC/$880DF2` variants). Then a Huffman table: a first byte with bit 7 set (low nibble = pixel value) followed by (second byte, code byte) pairs; second byte bits 6-4 = run length - 1, bits 3-0 = code length (1-8); the code is right-aligned in its byte; a byte ≥ `$80` where a second byte is expected starts a new first byte; `$FF` ends the table. The table is expanded into a 256-entry word table at `$FFBA00`. The data is a bit stream read with an 8-bit window: a window byte ≥ `$FC` escapes to a literal (3 bits of run, 4 bits of pixel); otherwise table[window] gives code length, pixel and run. | `hufftile.py` reproduces the VRAM contents of the font block exactly (1,440 of 1,440 bytes, plain variant) and of the attract fight's stage tile set `$9448BC` (header `$830E`, XOR variant) at VRAM `$1600` (6,256 of 6,256 longs); all 35 blocks of the two chains (8 stage sets, 27 UI blocks) consume exactly the bytes up to the next block |
| `$881038` | bytes to `(a1)+` (RAM, or the 32X frame buffer at `$840200`) | LZ with an 8-bit description byte, least significant bit first: 1 = literal; 0,0 = copy of 2-5 bytes from 1-256 back (offset byte); 0,1 = copy from a 13-bit offset with a 3-bit count (count 0 reads a count byte); a 16-bit field of 0 ends the block. ## 2. The frame structure (question 2)

### 2.1 Main loop and vertical-blank handler

Both are in RAM (`$FF0000`, `$FF0024`), copied from the cartridge (§1.1 step 7). In assembler terms:

```
FF0000  jsr   <state>            ; operand at $FF0002, rewritten by state code
FF0006  st    $8D00              ; "frame work pending"
FF000A  move.w #0,$8C1C
FF0010  move  #$2500,sr          ; levels 1-5 masked: only the vertical blank gets in
FF0014  addq.w #1,$8C1C          ; idle counter
FF0018  tst.b $8D00
FF001C  bne   FF0014             ; spin until the blank handler clears the flag
FF001E  bra   FF0000

FF0024  movem.l d0-fp,-(sp)
FF0028  move  #$2700,sr
FF002C  tst.b $8D00
FF0030  beq   FF0040             ; state not finished yet: skip the frame work
FF0032  sf    $8D00
FF0036  jsr   <vblank task>      ; operand at $FF0038, rewritten by state code
FF003C  addq.l #1,$8000          ; blank counter
FF0040  jsr   $FF4000            ; sound driver, EVERY blank
FF0046  move  #$2500,sr
        movem.l (sp)+,d0-fp ; rte
```

So one *state* runs per vertical blank at most. A state that finishes before the next blank is followed by the blank's task and the next state; a state still running at a blank (waiting for the SH-2s) just lets the blank run the sound driver and returns to it. There is no frame skipping: nothing counts blanks to catch up. `FF0050` (`st $8D00; spin`) is the same wait as a subroutine for states that need to wait mid-way.

The state is chosen by `movel #addr,$FF0002` and the blank task by `movel #addr,$FF0038`; every state ends by setting both. **Pairs observed** (the first column is a state, the second the task that follows it):

### 2.3 The picture cycle in a fight

Attract mode (states A = `$FF1152`, B = `$FF11AE`); the played fight is the same with `$0184` instead of `$0186`, the pad bytes added to B (`$FF0AB8`-`$FF0C66`) and the HUD/timer work added to A (`$FF08F2`-`$FF0A62`).

**Vertical-blank task after state B (`$FF13CC`)**: `move.w #$186,(a3)` (a3 = `$A15120`), `move.b #1,(a4)` (a4 = `$A15103`: CMD to the Master), read the VDP status. This is the only "go" signal. It is written right after the blank starts, so the frame buffer flip requested by state B has just taken effect.

**State A (`$FF1152`, runs right after that blank):**
1. `jsr $FF1006`: send the sound driver's two PWM request bytes to the Master as command 8 (§3.4), clear them.
2. `bsr $FF0846`: **clear the 320 × 240 picture area of the back buffer** with 240 auto fills: `$A15184 = $00A0` (161 words), then for each line `movem.w d0-d1,$A15186` (start address, data 0), 37 `nop`s, `dbf`; the start address begins at `$1000` and steps `$100` (256-word lines). The pacing is 16 + 4 + 148 + 10 = **178 cycles per line** (the emulator measures 178-186), 42,720 cycles for the picture, with no FEN poll. The book's formula gives 7 + 3 × 160 = 487 SH-2 clocks ≈ 162 68000 cycles per fill, so the loop is about 16 cycles slower than the fill.
3. `move.w #$8083,$A15100`: FM = 1, the frame buffer and VDP now belong to the SH-2s.
4. Music request if the wanted track changed (`$8C18` vs `$82`: `jsr $FF4008` with `d0 = 1`, `d1 = $82`).
5. `movel #$FF11AE,$FF0002; movel #$FF2A46,$FF0038; rts`.

**Vertical-blank task after state A (`$FF2A46`)**: sprite table DMA (128 words from `$FFB900` to VRAM `$F000`), then plane B: for each of 32 rows a 41-word DMA from the RAM panorama to `$C000 + 128 × row` with the source start advanced by the horizontal scroll in tiles (`$FF2AF8`-`$FF2B0E`; command words from the table at `$FF2B34`); then the scroll registers: HScroll words `$8C12`/`$8C14` at VRAM `$EC00`, VSRAM words `$8C0E`/`$8C10`. About 25,000 cycles in the emulator, mostly DMA stalls.

**State B (`$FF11AE`, runs after that blank):**
1. `jsr $FF005C`: read the pads. A Start press (bit 7 of `$8C03` or `$8C07`) leaves the fight (`$FF131A`: music stop, main `$89533A`, title).
2. `$FF11D4`: draw the "COPYRIGHT SEGA ENTERPRISES,LTD. 1993-1995" line if an easter-egg counter passes `$50` (§1.4).
3. `subq.w #1,$8C34; bmi` → leave to the ranking (`$FF126E`: music stop, main `$891E70`). The attract fight therefore ends after exactly 900 pictures.
4. Set the next pair (`$FF1152`, `$FF13CC`).
5. **Wait: `tst.b $A15120; bne` (`$FF122E`)**: until COMM0's high byte is 0. Interrupts are enabled here, so blanks come in while it waits (sound driver only).
6. `$8D02 = $A1512F`; if `$A1512E` (COMM7 high byte) is 1, the SH-2s say the match is over and the state leaves at once, as in step 3 (`$FF12C8`, no further wait). Otherwise `bsr $FF13B4`: if `$8D02` (COMM7 low byte) is 1 the next blank task is `$FF13EE` instead of `$FF13CC`; it writes the same go word and CMD but also calls `$88215A`, which copies palette sets into the 32X palette at `$A15220` (a palette change requested by the SH-2s).
7. `move.w #$83,$A15100`: FM = 0, the 68000 has the frame buffer again.
8. Copy the **mailbox** from `$840200`: 16 bytes to `$8B10`, a long to `$8424`, a long to `$8C28` (§3.6).
9. `eori.b #1,$A1518B`: **flip FS**.
10. `rts`; the main loop sets `$8D00` and waits for the next blank, which is the next "go".

| Measurement (PicoDrive, emulator) | Result |
|---|---|

| Video of frames 1000-1399: frames in which the 32X part of the picture (lower band: floor and fighters) changes | 196 of 399; gaps between changes: 194 of 2 frames, 1 of 8 |
| Same video, the Mega Drive sky band | changes at the other blank: the sky of picture *n* appears one frame **after** the fighters of picture *n* (the camera values come from the mailbox copied in state B, before the flip; the plane B DMA that uses them runs at the next blank 1, one frame after the flip took effect) |
| Time from the go to the 68000 seeing COMM0's high byte at 0, attract (846 pictures; `picturetime.py`) | min 1.19, median 1.39, mean 1.40, max 1.82 frames (histogram in tenths: 1.2: 17, 1.3: 250, 1.4: 349, 1.5: 154, 1.6: 64, 1.7: 10, 1.8: 2) |
| Same, played fight (1,101 pictures) | min 1.11, median 1.35, max **2.44** (1.2: 81, 1.3: 448, 1.4: 432, 1.5: 113, 1.6: 23, 1.9: 1, 2.4: 1) |

The earliest the 68000 can notice completion is when state B starts polling, about 1.19 frames after the go, so a picture done before the first look would be censored; only 1 of 846 attract pictures was (first look 1.13-1.19 frames after the go, median 1.19; `picturetime_by_frame.py`), so the left end of the histogram is real. The Master's own write of the busy flag, from a 15-picture event log, came 1.41-1.55 frames after the go. The window is 2.0 frames.

**What limits it.** In PicoDrive the limit is the design: two states, one per blank, so never faster than 30 a second. The SH-2s use 60-91% of the window in these scenes; one picture in 1,101 overran, and then state B kept waiting through a third blank, the picture lasted three frames, the sound driver kept running every blank, and nothing else happened (no catch-up). On a console the SH-2s have memory wait states that PicoDrive does not model, so the real ratio is unknown. If it exceeds 1.0 often, the pictures become 20 a second. I cannot say from the 68000 side.

**Everything is counted in pictures**, not blanks: the round timer (`$FF0FC2`, once per state A: BCD, subtract 4, 3, 3 on successive pictures from `$842A/$842B` = 10 hundredths per 3 pictures = exactly 1.00 s per 30 pictures), the demo length (`$8C34`). A late picture slows the game and its clock together; the 68000 never looks at real time.

### 2.5 The 68000's own load per picture (instruction arithmetic, emulator cycle counts)

Of a 2-frame picture (255,712 cycles): the clear 42,720 (17%); the blank-1 handler about 25,000 (10%); the poll in state B about 19,500 (8%); the sound driver runs in every blank (not measured; the PC profiler is unusable for this, §0); pad reading, command 8 and the HUD (played fights, `$FF1F66`) a few thousand cycles. The rest is the idle spin at `$FF0014`. The 68000 is not what limits the picture.

### 3.3 The two handshakes (code)

**Simple command**, e.g. `$FF1006`/`$FF102A`, `$8811BA`-`$8811D8`:
```
wait:  tst.b  $A15121 ; bne wait      ; Master has taken the last one
       move.b #cmd,$A15121            ; byte write: the high byte (picture flag) is left alone
       move.b #1,$A15103              ; CMD interrupt, Master only
wait2: tst.b  $A15121 ; bne wait2     ; taken
```
Parameters are written to COMM1-COMM7 **before** the command byte, with the same wait first (`tstb $A15121; bne` precedes parameter writes in `$893xxx`).

**Picture command**, e.g. `$8811EE`-`$881204`, `$FF13CC`:
```
       move.w #$0186,$A15120          ; high byte 1 = busy, low byte = command
       move.b #1,$A15103              ; CMD to the Master
       ...                            ; (other work, other simple commands)
wait:  tst.b  $A15120 ; bne wait      ; high byte cleared: picture done
```
In the vertical-blank task the second half is not executed at once: the wait happens one blank later in state B. The observed acknowledgement sequence (emulator): the Master clears the low byte within about 13,000 cycles of the go (a simple command sent 13,000 cycles later finds it free), the high byte stays 1 for 1.2-1.8 frames, and a simple command (sound, command 8) written to the low byte in between is taken in about 240 cycles (`$FF1016`: `R a15121 = 08` at 122,966, `= 00` at 123,208). **So the Master handles simple commands while a picture is in progress.** `SH2.md` (§2.1, §3.2-3.3) gives the mechanism: commands with bit 7 clear (`$01`-`$10`) run *inside* the Master's CMD interrupt handler (which clears the byte on return, hence the 240 cycles) and nest inside whatever the Master is doing; commands with bit 7 set (`$82`...) only leave a mailbox word for the Master's main loop, which clears the low byte when it starts the command, and the high byte at the very end (`0x06000900`).

Nothing like Virtua Racing Deluxe's "the SH-2 sets a bit in COMM1, the 68000 clears it" exists here (§7).

### 3.6 SH-2 to 68000: every channel the 68000 reads

1. **COMM0 high byte** = picture done (§3.3).
2. **COMM7**: `$A1512F` → `$8D02`, the scene code (values 0-9 and `$C` seen at frame ends in the played run, 1-5 frames each; only 0 and 1 in the attract run). In the played fight `$FF0902` acts on two of them: **6** clears the intermission flag `$8D0A` and requests the stage music `$8C1A` if it is not already playing; **`$C`** (match over) runs the "winner stays" logic: with `d0` = player 1's round wins (`$8416`), `d1` = player 2's (`$8417`), `d2` = wins needed (`$8415`): equal, nothing; player 1 has enough: clear `$8D0B` (and the fight counter `$8428` if it was set) and clear player 2's slot flag `$8402`; otherwise if player 2 has enough: set `$8D0B` (counter cleared if it was clear) and clear player 1's slot flag `$8401`. **`$A1512E`** event bits read by `$FF0EE0`: **bit 0** leave the fight (back to the state saved in `$8B00`), **bit 1** new round (timer reloaded from `$8C42`, life values reset to `$70`, win-mark flags cleared), **bit 2** freeze the round timer (`$8D06`), **bit 4** player 1 won a round (`$8416++`, `$8418 = $FF`, HUD redraw), **bit 5** player 2 won a round. In the demo (`$FF1152`/`$FF11AE`) only `$A1512E == 1` and `$A1512F == 1` are tested.
3. **COMM2**: `$A15124` (non-zero: load the costume palette of player 1 (value 1) or 2, via `$882008`), `$A15125` (`$8D11`: 0 nothing, 1 → request music `$86`, other non-zero → `$87` at `$FF0988`, with the sound driver's request words cleared first); `$8D11` stayed 0 at every frame end of both runs, so this path was not exercised.
4. **COMM1-COMM5 after command `$0B`** (12 bytes into `$8464-$846C`).
5. **The frame-buffer mailbox** (below).

**Mailbox.** At the end of each picture the SH-2s leave data in the back buffer's spare area: byte `$200` of the frame buffer (`$840200`), inside the gap between the line table (`$0000-$01FF`) and the first picture line (the 68000's line table starts line 0 at word `$1000`, byte `$2000`, with 256-word lines, 240 lines, which fills the whole 128 KB). The 68000 copies, after taking FM:

| Mailbox offset | Copied to | Content as read |
|---|---|---|
| `+0..+15` | `$8B10-$8B1F` | not read by any code I found; contains `C000`, a smoothly changing 16-bit value (`$407A`, `$4262`, `$43F7`, … looks like a camera quantity), and the same horizontal angle that follows at +20 |
| `+16` (long) | `$8424` | life values: word `$8424` player 1, word `$8426` player 2 (`$70` = full = 112; read in the HUD by `$FF2690` and following) |
| `+20` (long) | `$8C28` | camera: word `$8C28` (background height: `$FF2A92`-`$FF2AC6` computes `7v/128 - 20`, i.e. `v>>4` times ½ + ¼ + ⅛, and clamps it to ±256) and word `$8C2A` (background angle: `-$8C2A >> 6`, masked to 1,024, gives the tile column of the panorama window, the low 3 bits give the fine scroll) |
| `+24` (long, played fight only) | `$8B08` | BCD counter (`00000007`, `00000010`, `00000014`, … +3.33 a picture), shown on the right of the HUD |

The demo copies 24 bytes, the played fight 28. Nothing else flows back. The 68000 reads it only after FM = 0. **Reconciled with `SH2.md` (second pass):** there are two writers, both on the Master. `0x06009800` copies the 16-byte block `0x06029C24` to `+0..+15` (the 68000 never reads it); the task `0x06018B6C` writes `+16/+18` (life, scaled to 0-112), `+20/+22` (camera) and `+24` (counter). See `SH2.md` §3.1.

### 3.7 What is not used

- **No DREQ/FIFO** (`$A15106/7`, `$A15108-$A15112` written once, with 0). Virtua Racing Deluxe sends 1,280 words by FIFO every picture; here nothing but 8 bytes of COMM data and a command.
- **No RV** (`$A15107` bit 0 never set) and so no Mega Drive DMA from the cartridge: all 37,194 VDP DMAs of the played run, and all 31,748 of the attract run, read work RAM (VDP register 23 = `$7F`; sources `$FF90BC-$FFBFFF`). Lengths: 41 words (35,840), 128 (1,294), 64 (59), 448 (1). Tile and picture data from the cartridge is written by the CPU through the decompressors (no DMA from ROM at all).
- **No INTS**, **no PWM**, **no `$A1518A`**.
- **No use of the Z80 for 68000-SH-2 traffic.**

## 4. The game logic the 68000 holds (question 4)

**How far I got:** all of the in-fight 68000 code is read (`$FF08B4`-`$FF2BB3`, `$881C7A`-`$881E5F`, the sound and communication stubs); the menu, option, name-entry and ranking scenes (`$88E3xx`-`$89Cxxx`, about 70 KB of scene code) were read only where they send commands. What follows is complete for fights and attract mode and a sketch for the menus.

### 4.1 What is *not* on the 68000

No fighter state machine, no hit or collision test, no camera, no AI, no motion data, no model data, no random numbers for combat (the 68000's generator `$8004` is used for the random stage in one mode, §4.5). Evidence:

- The code that runs during a fight is the list in §2.3 and nothing else. The coverage list of every PC the 68000 executed in the 3,600-frame attract run (1,913 distinct PCs; `prof_all.csv`) holds the loop, the pad code, the HUD, the DMA task, the sound driver, the scene code, and no code that touches fighter state.
- The attract fights run with **no input from the 68000**: COMM1 is cleared on entry (`$FF111E`) and never written again. Both fighters are driven by the SH-2s.
- Per picture the 68000 sends at most **2 pad bytes + 1 replay-flag byte + 2 sound bytes** (5 bytes of data) plus a command word and a sound command byte, and gets back **up to 4 status bytes in COMM and 24-28 bytes of mailbox** (§3.6). A pose of two fighters (two dozen joints each) does not fit in that, and no routine here builds one.
- The only per-fighter information the 68000 ever holds are two life values, round-win counters, a score-like counter, two fighter numbers and two "slot in use" flags, all supplied or consumed as in §3 (the slot flags and the win counters give it the arcade's "winner stays" bookkeeping, §3.6).

So the poses the SH-2s draw are computed on the SH-2s from their own data (the 2.9 MB after the SH-2 image is read only by them). **For the chapter: this game is the extreme of "68000 as I/O processor".** Whether one SH-2 or both run the simulation and the drawing is `SH2.md`.

### 4.2 Input

`$FF005C` (called by every state that needs input) reads both ports through `$FF016C` (TH-toggling read, 6-button aware), once per state:

- A port is read only if its device id (`$8203`/`$8204`, filled by `$FF01EE` through `$FF028E`) is `$0D`; otherwise its pad word is zeroed. Unknown devices read as no input.
- Pad word (`$8C00`, `$8C04`): low byte = Start, A, C, B, Right, Left, Down, Up (1 = pressed); high byte = the Z, Y, X, Mode nibble of a 6-button pad, with bit 15 set when the pad is 6-button.
- `$8C02`/`$8C06` = bits that went from 0 to 1 since the last read.
- **Remapping** (`$FF00B8`; or `$FF00E4` while the intermission flag `$8D0A` is set, which is the same without removing Start): the layout byte `$8224`/`$8225` selects one of four handlers (`$FF0108`: layouts 0-3) which, for a 6-button pad only (bit 15 of the pad word), can move buttons X/Y/Z onto the fight buttons, and the byte is rotated by 4. **The bytes sent to the SH-2s (`$8D0C`, `$8D0D` → `$A15122`, `$A15123`) are: bits 7-4 Right, Left, Down, Up; bit 3 Start (only in the `$FF00E4` variant); bit 2 A, bit 1 C, bit 0 B** (values `$10`, `$20`, `$40`, `$01`, `$02` seen from the scripted input).
- **Start**, in a played fight: if the player's slot flag (`$8401` for pad 1, `$8402` for pad 2; non-zero = in use, inference) is set, a new Start press pauses (`$FF0CC8` / `$FF0D26`: sound call 8, `$8413 = 4`, state `$FF0D84`/`$FF0DFC`); in the pause state Start unpauses (`$FF0E74`, sound call 9) and the d-pad is forwarded as command `$10` with a direction code 1-4. If the slot is not in use, Start is a "join" request: stop the music (sound call `$C`), set `$8D10` and `$8D0A`, and set bit 3 of that pad's byte so that the SH-2s see Start (`$FF0B30`/`$FF0BA8`).

### 4.3 The round timer and the counters

`$FF0FC2`, once per state A of a played fight: if `$8D06` (frozen by the SH-2s) is 0 and `$842A != $9999`, the BCD pair `$842A/$842B` is decremented with `sbcd` by 4, 3, 3 on three successive pictures (table `04 03 03` at `$FF1002`, phase in `$8C32`): 10 hundredths per 3 pictures, so 1.00 s every 30 pictures. The start value is `$3000` (`$8C42`; "30" seconds). There is no test for 0 on the 68000; the SH-2s announce the end of the round (COMM7 bits, §3.6) and the 68000 reloads the timer on the "new round" bit. The HUD shows `$842A`, drawn in `$FF249C` as four tiles from the digit table at `$988DE0`/`$988E08`.

`$8416`/`$8417` count round wins (increments on COMM7 bits 4 and 5), `$8415` is the number needed; `$FF2502` draws that many round marks per player.

### 4.4 The HUD (`$FF1F66` and callees; played fights; in the attract fights planes A and B hold only the sky, so the "PRESS START BUTTON" text there must be 32X)

All of it is Mega Drive plane A (VRAM `$A000`, 64 × 64 cells in fights) plus a few sprites, written by the 68000 each picture:

| Routine | Draws |
|---|---|
| `$FF2690`, `$FF26E0`… | two life gauges, 14 tiles each, from `$8424`/`$8426`: value ≫ 3 = whole tiles, value & 7 selects the partial tile (tables at `$98708A`, `$9870AE`) |
| `$FF249C` | four timer digits at plane A cells (`$FF24BC`-`$FF24FC`; sprite helper `$FF27F4`) |
| `$FF2502` | round-win marks for both players |
| `$FF1FB2`-`$FF20BE` | the `$8B08`/`$8B0A` figures (two and four BCD digits) from the table at `$98983C` |
| `$FF2408`, `$FF2456` | blinking markers and the fighter names (`$9870F2` table indexed by `$8411`/`$8412`) |
| `$FF2108`-`$FF2260` | text tiles on plane A selected by the HUD mode bytes `$8413`/`$8414` and the BCD counter `$8428` (which captions exactly: not decoded; the large yellow "FIGHT 1" and "TIME OVER" banners in the video are 32X graphics) |

The HUD costs the SH-2s nothing and is changed on the 68000's schedule.

### 4.5 Scene flow and the arcade ladder (a sketch)

- **Ladder:** `$8C24` (0-8) is the position. For a slot that is not in use (CPU) the fighter is `[4,2,5,1,7,3,6,0,8][$8C24]` (table at `$881482`, `$881212`-`$881270`), and **the same number is the stage** (`$8C1E`; each fighter has a home stage). The music per stage is `[$8A,$88,$8C,$8D,$85,$81,$8E,$89,$84][stage]` (table at `$881DFC`). Stage data comes from the 9-entry table at `$FF2600` (§1.3; entry 8 repeats entry 0). In a played fight the 68000 requests the stage music when the SH-2s report scene code 6 (`$FF0902`), and the result themes `$86`/`$87` from COMM2's low byte. The attract fights use music `$82`.
- **Random stage** (`$8816BA`): `jsr $FF0436` with `d0 = 8` picks one of eight stages for the mode that also sets record mode (`$8D14 = 1`).
- **Player select** (`$893040` and neighbours): all drawn by the Master on commands 5, 6, 7 (pictures at fixed positions, names and portraits from pointer tables at `$893E90`-`$893EFC`), cursor logic on the 68000.
- **Ranking:** a RAM table initialised at boot (`$892532`), shown with plane A text over the Master-drawn title picture.
- **Options:** the 14 bytes at `$820A`-`$8213` and the button layout bytes.

### 4.6 Record and replay of input

`$FF10A6`/`$FF10C0` store or fetch the two pad bytes at the pointer `$8B30` (buffer `$FFC400` to `$FFEFFF`, 11,264 bytes, 5,632 pictures, about 188 s at 30 a second). `$8D14` = 1 records (set at `$8816A8`, with the random stage), 2 replays (set at `$881838`); `$8D14` was 0 at every frame end of both runs, so neither mode was exercised. In replay mode COMM3's high byte carries the OR of the live pad bytes. Two bytes per picture is all that is needed to reproduce a fight, which means the simulation on the SH-2s is **deterministic given the pad bytes** (inference: nothing else is stored). The attract mode does not use this buffer (it sends no pads).

### 4.7 Fixed point and formats on the 68000 side

Nothing in the 68000's data is fixed point worth the name: life is an 8-bit value (full = `$70` = 112), camera values are integers whose scaling is read off in `$FF2A74`-`$FF2AC6` (angle: `-v >> 6` gives pixels of a 1,024-pixel panorama, vertical offset `7v/128 - 20` clamped to ±256 for `$8C28` = v), timers are BCD. Their meaning in the SH-2s' units is for `SH2.md`.

## 5. Mega Drive VDP and 32X compositing (question 5)

### 5.2 What each layer holds

| Scene | Plane B (`$C000`) | Plane A (`$A000`) | Sprites | 32X layer (video) |
|---|---|---|---|---|
| SEGA logo, AM2 logo, title (frames 13-889) | empty | empty | none | the logos and the title picture (Master, command 5) |

| **fight** (frames 967+ attract, 962+ played) | **sky, clouds, sea**: 32 rows × 41 cells (1,312 entries, 16-65 distinct tiles) re-sent by DMA every picture | **HUD** (played): 432-434 entries, 23-25 distinct tiles: life gauges, timer digits, round marks, names, `$8B08` figures; **empty in the attract fights** | 2 sprites at x = 1 (off screen) | **fighters, floor and the ring, "FIGHT n", "TIME OVER", "PRESS START BUTTON"**; index 0 where the Mega Drive shows through |

Tile VRAM: the stage's Huffman tile set (366-800 tiles) is loaded at VRAM `$1600`; the font and UI tiles are loaded at scene start from the 27-block chain (§1.3). The panorama tilemap is decompressed into RAM at `$FF90BC` (stage load, `$FF258E`; the attract fight's stage 4, 6,720 bytes, matches `kosdec.py`'s output of `$98297C` exactly). It is **168 cells wide and 20 rows high** (row stride `$A8` words, `$FF25D6`); a table of 32 row pointers at `$FF9000` maps the plane's 32 rows onto it (the first source row is repeated `d5` times at the top, the last at the bottom: sky and sea). The 32 row DMAs pick a 41-cell window from their source row each picture, starting at column `(-$8C2A >> 6 & $3FF) >> 3`, 0-127 (so 128 + 40 repeated cells make the 360° turn seamless). The background is therefore scrolled by moving the window, not the plane; only the sub-tile 0-7 pixel scroll goes through the scroll registers (inference from the DMA source addresses `$FF90BC`, `$FF90BE`, … advancing by 2 bytes as the window moves).

### 5.4 The 32X side as set from the 68000

| Item | Value |

| DREQ, RV | none; the 68000 never writes the frame buffer except line tables, the two 71,680-byte pictures and its clears |

**On the "HUD costs the SH-2s nothing" idea in `src/32x/compositing.md`:** here it is stronger. The HUD, the sky and the sea are 68000 work; the clear of the back buffer is also 68000 work, which moves 0.33 frame of fill and write time off the SH-2s per picture. The cost is hidden: FM = 1 arrives 0.44 frame after the go (§2.3), but `SH2.md` §3.5 shows the SH-2s spend those first cycles on game logic, collision and the transform stage (the first frame-buffer write is the Slave's, about 98,000 cycles after the go), so the 68000's clear overlaps their logic phase completely.

The title and logos have no music in these runs | code, emulator |

### 6.2 The PWM request path

The driver's work area (`$FF5D16`, pointer in `$FF400C`) holds two request words at `+4` and `+6` (`$8824`, `$8826`, `$8827` seen: high byte `$88`, low byte a number `$24`-`$28`). The driver writes them for `$EE`-class PWM events in the sequences (the Qsound switch `$01FF`/`$02FF` at `$FF493E`/`$FF494E`, volume-dependent words `$80FF`…`$88FF` from the table at `$FF5998`). Once per picture, `$FF1006` (fights, command 8) or `$FF101A` (menus, command 2) sends the **low bytes** of the two words as COMM4 (`word +6` low → `$A15128`, `word +4` low → `$A15129`) after waiting for the Master, and then clears both words; so a request lives in RAM for at most one picture. In my runs the bytes are `00` almost always and `24`, `26`, `27`, `28`, `4A`, `4D`, `30`, `7F` at the start of fights (a handful per fight); what the SH-2 does with them (which PWM sample or voice) is for `SH2.md`.

Menu and logo sounds are not the driver's: the code sends command 2 with constants (`$F4` at the SEGA logo, `$F5`/`$F6` for the cursor).

### 6.3 Comparison with `src/megadrive/sound.md`

The book's VRD row says: sequencing on the 68000, once per frame; FM/PSG written by the 68000 holding the Z80 bus; the Z80 plays samples. VF matches the first two (and says "Sega's V3" is one of the book's rows already), and differs on the third: the Z80 plays nothing; the sample-like sounds are on the SH-2s' PWM, requested through the 68000. The 68000 holds the Z80 bus around each batch of FM writes (`$FF403A`, `$FF4042`: bus request and wait, `$FF40B6`: release), as in the book's description of V3.

### 7.1 What the retail ROMs say about claims the book makes "by the VRD project's account"

All statements below come from the retail VRD's 68000 side (and, where stated, VF). They do not test anything on the SH-2s.

- **"One state per vertical interrupt, and a new picture every third": confirmed**, as a frame loop (the RAM stub runs one `jsr state` per blank) and as a rate (859 pictures in 2,574 frames).
- **"Flip only when the SH-2s have signalled that the picture is drawn; if not, wait another interrupt": confirmed** (`$881D70`-`$881DB4`: no flag, no flip, return; the next blank tests again).
- **"The 68000 sets, the SH-2 clears": not what the retail 68000 does for its waits.** It sets COMM0 once and waits on flags the SH-2 sets in `$A15123`, clearing them itself. (`SH2.md`/the SH-2 side may still clear COMM0; the 68000 never looks.)
- **"About 14 block copies to the Master and 21 pixel jobs to the Slave per picture, each a COMM handshake": not visible from the 68000.** The retail 68000 makes **one** COMM command and one 1,280-word FIFO transfer per picture, and raises no CMD interrupt in the attract race. If the jobs exist they travel inside the FIFO block or between the SH-2s. (The project's ROM file differs from this retail one only in 103 SH-2 bytes, so the 68000 code of the file it matched is the retail code; its later source may have changed more.)
- **"The Master polls a communication port": consistent**: nothing wakes it by CMD interrupt while the race runs.
- **"The 68000 sequences, FM/PSG with the Z80 bus held, the Z80 plays a 653-byte sample player": the 653 bytes are confirmed** (two uploads of exactly 653 bytes at `$8B0C1E`); the Z80-side mailbox bytes I saw are at Z80 `$0FFD`/`$0FFE`, not "at the top of sound RAM" (`$1FFD-$1FFF`); I did not read the Z80 program, so this may be the Z80's own view of the same bytes.
- **"The game itself never calls the driver; requests go through mailbox bytes passed on once per frame": not examined.**

## 8. Open questions and suspicions (question 8)

Settled on the 68000 side but needing the SH-2 side to be useful are marked "SH2".

1. **SH2.** Most command meanings are now in `SH2.md` §3.2-3.3 (read from the Master's tables); those marked "not run" there (`$0A`, `$0D`, `$0E`, `$10`, `$0188`-`$018D`) are still their inferences, and I never saw the 68000 send most of them. Still open: what the Master and Slave each do between the go and the clear of COMM0's high byte (`SH2.md` §3.5 has the sequence), whether the Master waits for FM = 1 before drawing (their timeline has the Master drawing from +95,700 and FM = 1 at +55,600, so it does not need to), and the format of the command-6/7 images (`FF E0 00 22 …`).
2. **SH2.** The 24/28-byte mailbox: which SH-2 writes it, what the 16 bytes at `+0` mean (copied to `$8B10`, no reader found), and who decides "TIME OVER": the 68000 counts the displayed round timer by itself and never tells the SH-2s its value (no COMM word carries it), so the SH-2s must count the round separately; check in `SH2.md` that the two stay in step, and what happens when a picture is late.
3. Whether the 68000's clear loop (178 cycles per line) is slow enough on a console: the book's formula gives a 161-word fill 7 + 3 × 160 = 487 SH-2 clocks ≈ 162 68000 cycles, so it should be, but the loop never reads FEN. Untested on hardware, as is everything about the frame rate.
4. How often a real console exceeds the 2-blank window (PicoDrive: 1 picture in 1,101 of a played fight, none in 901 attract pictures; no SH-2 wait states modelled). If often, the game, whose clocks run per picture, would slow below real time.
5. Why the driver copies music into Z80 RAM (my guess: to keep the sequencer's reads off a cartridge the SH-2s also use). Not tested: I did not see whether a change in access pattern would show in PicoDrive.
6. What `$8D14` = 1 and 2 are used for in the game (record at match start, replay at `$881830`): the user-visible feature is not identified (probably a replay of the last fight, which would make the simulation deterministic in the pad bytes).
7. The scenes I did not exercise: VS mode, tournament, options, name entry, the pause list, commands `$0188`-`$018D`, `$04`, `$07`, `$0A`, `$0B`, `$0D`, `$0E`. Their code is in `$88E3xx`-`$89C8xx` and `$89Axxx`; I read their command sends, not their logic.
8. The word-oriented tilemap decompressor (`$880E50`) is not verified by a decode.
9. PAL: refused by static reading; not run. NTSC 224-line mode only; the 240-line line table is for the 32X buffer geometry.
10. `$8C52` and the copyright text: an easter egg or a debug screen (80 presses of pad 2's A button show it); only the counter was read.
11. The 4 MB cartridge: only the first MB is reachable by the 68000; `$030000-$03FFFF` and `$0A13C5-$0C7ED9` (and `$06DD0E-$06FFFF`) are not referenced by any 68000 operand: probably SH-2 data inside the first megabyte, not identified.
12. I did not run the game on any real hardware; every time figure is PicoDrive's, and the only SH-2 timing used is the fraction of a 2-frame window.
