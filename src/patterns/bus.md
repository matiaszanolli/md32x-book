# Living with bus contention

Four processors and two video chips share the machine's memories, and none of them waits politely. When a 68000 access to the cartridge is slow, it is usually slow because an SH-2 got there first; when an SH-2 write to the frame buffer stalls, it is because the 32X VDP is reading that buffer to make the picture. A program can be slowed down by what the *other* processors are doing, not by anything it is doing itself. The prices of every access are in [Access timing per CPU](../32x/timing.md#the-figures); this page is about what real programs did with those prices. The short version: on a machine this crowded, where code and data live *is* the optimisation.

Every figure here is counted in the clocks of the CPU that pays it. Unmarked figures are SH-2 clocks (23.01 MHz on NTSC machines); 68000 clocks (7.67 MHz) are marked as such, and each one lasts three times as long ([timing](../32x/timing.md#the-figures)).

Four fights cover most of it:

1. **The 68000 against the SH-2s, over the cartridge.** Both sides run code and read data from the same ROM. When they collide the SH-2 wins and the 68000 waits [32X-HWM §4.1 p.74].
2. **The two SH-2s, over one bus.** SDRAM, the frame buffer, the cartridge and the registers all sit on one external bus, so a Slave access waits while the Master is using it, and the other way round [SH7604 §7.10; [Two SH-2s, one bus](../sh2/bsc.md#two-sh-2s-one-bus)].
3. **Everyone against the VDP, over the frame buffer and palette.** The VDP holds the displayed buffer while scanning it out, refresh closes it in bursts, and an auto fill keeps it busy for the fill's whole length [32X-HWM §4.4 p.77].
4. **On the Mega Drive side, the 68000 against the Z80 and the Mega Drive VDP's DMA.** An older fight with older rules, but in 32X mode it runs into the first one: a DMA from the cartridge needs RV, and RV shuts the SH-2s out of the cartridge ([below](#the-mega-drive-side)).

The examples carry different weight. Motocross Championship, Knuckles' Chaotix, Mortal Kombat II, Star Wars Arcade and After Burner Complete are commercial releases, read from clean retail dumps: what they do ran on consoles, though not always well. The ECCO CinePak demo and the Runlength Mode Test are Sega sample programs from development cartridges that were never sold. d32xr, an open-source Doom port, and the S32X-SKILL notes are homebrew; d32xr's commit history records fixes made on consoles, while the skill's notes were tested mostly in PicoDrive. The Virtua Racing Deluxe project and the Aerobiz Ultimate project are the author's work in progress and have not yet run on a 32X, so what they report is tagged <span class="tag emulator">emulator</span>. Where this page says what Virtua Racing Deluxe itself does, that is the project's account of the game, from a ROM copy the project has patched ([VRD-NOTES](../appendices/bibliography.md#vrd-notes)).

## What each program did

The clearest way to see the tactics is what each program chose to put where.

**d32xr keeps the 68000 out of the cartridge.** Its 68000 main loop is copied into work RAM at startup, with a build note that it has to live there to stop the two SH-2s contending with it for the ROM [D32XR, main.c, crt0.s]. The SH-2s own the cartridge, and even then the game does not read textures from it while drawing: a texture cache copies the most visible textures into SDRAM a few per frame, nearest surfaces first, and swaps each texture's data pointer to the RAM copy so the drawing code never knows which copy it holds. Evicted entries get their ROM pointer back [D32XR, r_cache.c, r_phase9.c]. Levels larger than the directly mapped ROM window are paged through 512 KB cartridge bank windows, re-selecting the page on entry to the code that walks each structure [D32XR, marsnew.c, p_setup.c]. This is also the standard shape for multi-megabyte games on a 256 KB machine: immutable data — decoded graphics, palettes, music, levels — stays in ROM and is read in place at `0x02000000`, where it is cacheable and read-only; only mutable state goes to SDRAM [S32X-SKILL, architecture].

**Motocross Championship runs the other way, from ROM, and pays for it.** Both of its SH-2 programs execute in place from the cached cartridge window instead of being copied to SDRAM [MCX, user header and entry points]. It works because the cache absorbs the hot loops — even the Slave, parked in a two-instruction loop in ROM all game long, only fetches that loop from the cartridge once before the cache holds it. But every cold path pays cartridge misses (a cache line from ROM costs up to 136 SH-2 clocks against 12 from SDRAM, see [timing](../32x/timing.md#the-figures)), and it competes with the 68000, which is also running from the cartridge. The rest of the game is textbook placement: the Master renders into an SDRAM staging buffer and then makes one bulk transfer of about 64 KB to the cache-through frame buffer each frame, instead of writing pixels to the frame buffer as it draws [MCX, headless runs].

**The ECCO CinePak demo streams through the cache-through window on purpose.** Its movie is read directly from the cartridge at the *cache-through* address (`0x22020000`), so megabytes of sequential frame data flow through the SH-2 without ever evicting code from the cache [ECCO, decoder entry]. It is not free: the decoder reads the stream a byte at a time, so every byte is a whole cartridge access, about twice the bus time the cached view would cost per byte. What it buys is a cache that keeps the decoder's code and tables ([Cache discipline](cache.md#what-a-read-costs-through-each-view)). Decoded frames are built in SDRAM and copied to the frame buffer one longword at a time, with five `nop`s after each store [ECCO, blit routine at `0x06000238`]. Those are idle clocks, not work, and by the manual's rule (below) idle clocks can at best pay for themselves: each one takes at most one clock off the next write, and none once the write is down to its 3-clock floor. The loop's own load, pointer step, counter and branch already sit between the stores. On the manual's figures the `nop`s cost five clocks per longword and gain nothing back; what Sega meant them for is not recorded. And with the Slave parked, the demo never has two SH-2s fighting over the bus at all.

**The Runlength test attacks the frame buffer itself.** Its polygon renderer writes the display data in the VDP's run-length mode: one word per run of same-colour pixels, which the VDP expands while scanning out ([the VDP chapter](../32x/vdp.md#run-length)). A flat-shaded object's frame buffer traffic shrinks by whatever the average run length is, and the whole engine and its tables live in SDRAM [RLT, renderer]. This is the most literal answer to "the frame buffer is slow": write less of it.

**Knuckles' Chaotix lets the hardware do the clears.** Blanketing a frame buffer with a solid colour costs tens of thousands of bus cycles if a CPU writes every word, but the VDP's own fill does it in 7 + 3 × length SH-2 clocks while the CPU works elsewhere ([auto fill](../32x/vdp.md#auto-fill)). Both Chaotix and Motocross Championship blank their buffers that way at boot, two buffers each with the page bit toggled between [MCX, 68000 boot; CHAOTIX, headless runs]. During play, Chaotix's Master hands the per-frame clear to its Slave: it writes a command byte, and the Slave issues 216 auto fills, one per line, waiting for each to finish, while the Master gets on with its own work. Between commands the Slave polls that byte with a 99-pass delay loop between reads, so its poll costs one register read every few hundred clocks instead of one every few [CHAOTIX, SH-2 code at `0x060002D4`-`0x060002FC`, `0x0600032C`-`0x0600035E`, `0x06004B12`, `0x06004B9A`].

**Mortal Kombat II shows the bill for doing it badly.** Its Master starts each 256-word auto fill and then polls the FEN bit until the fill finishes, 161 times a frame. By the manual's fill formula that is 161 × (7 + 3 × 256) ≈ 125,000 clocks of waiting that the fill was supposed to overlap [32X-HWM §3.3, FILL function]. The Master has about 384,000 clocks in an NTSC frame (23.01 MHz ÷ 59.92 frames a second; see [System architecture](../megadrive/architecture.md) for the frame rate), so the clear spends a third of its frame polling. Its Slave's main loop reads a communication register back to back with no delay, taking bus cycles the Master wants for SDRAM, and the Master's command handler busy-waits through 67 port handshakes to receive one state block [MK2, `0x060010DC`, `0x06005178`, `0x060003F4`]. None of it is wrong; all of it is bus time somebody else wanted.

## Moving data without paying twice

- **Batch and align frame buffer writes.** Every access to the frame buffer is a bus transaction, so pack four 8-bit pixels into one aligned longword and unroll the store loop; keep tiles on 4-pixel boundaries so a tile row is exactly four aligned stores <span class="tag emulator">emulator</span> [S32X-SKILL, optimization notes]. An SH-2 frame buffer write goes through a small write buffer: 3 clocks while it has room, 5 when it is full. The 5 assumes writes back to back; each idle clock before a write takes one clock off it, but never below 3 <span class="tag manual">manual</span> [32X-HWM §4.4 p.77]. So an empty gap only buys back what it costs. What wins is putting work the loop needs anyway (the next pixel's arithmetic, the pointer updates) between the stores, so that the buffer drains while the CPU is busy rather than idle. How deep the buffer is remains <span class="tag disputed">disputed</span> ([discrepancy 4](../appendices/discrepancies.md)).
- **Let DMA carry the big copies.** Frame buffer fills and sample streaming through the SH-2's DMA run without the CPU, and the CPU can compute while they move [S32X-SKILL, optimization notes; [DMA controller](../sh2/dmac.md)]. For 68000-to-SH-2 bulk data the [DREQ FIFO](../32x/fifo.md) is the intended path.
- **Treat RV as a shutdown, not a tool.** RV hands the cartridge back to the Mega Drive VDP for DMA, and while it is 1 any SH-2 access to the cartridge stalls until the 68000 clears it [32X-HWM §4.1 p.74]. d32xr's header makes that a rule for both CPUs: no ROM reads while RV is set, whether from code, DMA or interrupt handlers [D32XR, marshw.h warning]. Interrupts are only at risk where the vector table or the handler is in the cartridge. A program the boot ROM copies to SDRAM normally keeps both there (Mortal Kombat II's vector tables are at `0x06000000` and `0x06000120`, Chaotix's at `0x06000000` and `0x06000080`), but Motocross Championship runs from the cartridge with both vector tables in ROM, so any interrupt it took during an RV window would stall too [MK2, vector tables; CHAOTIX, Slave entry and dispatch; MCX, user header and entry points]. The Aerobiz Ultimate project needs RV windows for Mega Drive DMA, so it keeps its SH-2 code in SDRAM, where the windows cost the SH-2s nothing as long as they do not touch `0x22000000` meanwhile [AU-NOTES, PORT_ARCHITECTURE]. The other way out is never to set RV. The Virtua Racing Deluxe project reports that the game does no DMA from the cartridge to VRAM, the transfer RV exists for, and that every write it makes to the DREQ control register sets only 68S, for FIFO transfers the 68000 feeds by hand, so the project's own SH-2 code can safely run from the cartridge [VRD-NOTES, KNOWN_ISSUES]. If you want the cartridge to yourself, the question is what everyone else will be executing meanwhile.

## Two SH-2s, both working

Parking the Slave in a loop its cache holds, as the ECCO demo does, ends the second fight by forfeit. When both SH-2s have real work, the programs read for this book keep each CPU on memory the other does not need:

- **Keep the hottest loop off the bus.** Cache hits and on-chip RAM never use the shared bus, so two SH-2s working from them do not slow each other at all ([Two SH-2s, one bus](../sh2/bsc.md#two-sh-2s-one-bus)). Star Wars Arcade's Slave cuts polygons into trapezoids in a routine it keeps in its 2 KB of on-chip RAM, and leaves the pixel writes to the VDP's auto fill, while the Master transforms the next frame [SWA, SH-2 code at `0x060008F0`; [Splitting work across three CPUs](cpu-split.md)].
- **Share little, once a picture.** Star Wars Arcade's Master writes polygon lists into one of two buffers while the Slave reads the other, and the Slave purges its cache once per picture, before reading each list [SWA, SH-2 code at `0x06000E96`-`0x06000ECE`, `0x060007D0`]. After Burner Complete goes further: its Master draws, its Slave mixes sound, and the two share no SDRAM at all [AB32X, SH-2 program].
- **Read shared data once.** Data both SH-2s use costs a full burst for each uncached read, so read it once through `0x26000000`, or purge just the lines the other CPU wrote, as d32xr mostly does ([the placement table](../32x/timing.md#where-things-should-live); [Cache discipline](cache.md)).
- **Do not run DMA on both at once.** If both SH-2s run DMA at the same time, one of them slows to a crawl until the other finishes <span class="tag manual">manual</span> [32X-HWM §5.3, DMA restrictions].

No source measures what the two SH-2s cost each other on a console, and no emulator models it (see [below](#what-emulators-do-not-show)). d32xr, where both CPUs draw walls from the same lists, is the open case ([Splitting work across three CPUs](cpu-split.md#open-questions)).

## The Mega Drive side

The 68000's older fights still happen in 32X mode, and two of them reach the 32X side. The full rules are in [Z80 bus control](../megadrive/z80.md) and [DMA](../megadrive/vdp-dma.md).

- **DMA from the cartridge needs RV.** In 32X mode the Mega Drive VDP can only DMA from the cartridge with RV = 1, which stalls the SH-2s' cartridge accesses (above) and removes the `$880000` window the 68000's own code normally runs from [32X-HWM §3.1 pp.13-14; [The RV bit](../32x/architecture.md#the-rv-bit)]. So the code that starts the DMA runs from work RAM, the SH-2s keep to SDRAM for the duration, and since the transfer stops the 68000 until it ends, big ones belong in vertical blank ([What the VDP and DMA do to real speed](../megadrive/m68k.md#what-the-vdp-and-dma-do-to-real-speed); [How much fits in a frame](../megadrive/vdp-dma.md#how-much-fits-in-a-frame)). A DMA from work RAM does not need RV at all.
- **The Z80 borrows the 68000's bus.** Every Z80 access through its bank window is a 68000 bus cycle that holds the 68000 off, and the manual applies the cartridge competition with the SH-2s to the Z80 as well [32X-HWM §4.3 p.76; [timing](../32x/timing.md#the-z80)]. Keep the Z80 working from its own RAM. d32xr's 68000 unpacks the music into work RAM and, holding the Z80's bus, copies it into Z80 RAM in 512-byte blocks; the Z80 then plays the music's commands from its own memory [D32XR, src-md/vgm.c; src-md/crt0.s `bump_fm`; src-md/z80_vgm.s80]. Z80 *writes* to the 32X are a separate hazard ([The Z80's view](../32x/architecture.md#the-z80s-view)).

## Sharing without colliding

The memory map leaves only three channels the 68000 and the SH-2s share: the 16 communication bytes, the DREQ FIFO (68000 to SH-2 only), and the frame buffer DRAM under the FM arbitration bit. The SH-2 cannot see 68000 work RAM at any address, and the 68000 cannot see SDRAM [32X-HWM; VRD-NOTES, communication analysis]. (The two SH-2s share far more: all of SDRAM, which is the second fight.) The Virtua Racing Deluxe project lost three attempts to a work-RAM ring buffer before reading that page of the manual [VRD-NOTES, KNOWN_ISSUES]. Designing a structure shared between the 68000 and the SH-2s outside those three channels is not creative, it is broken.

**Frame buffer ownership is a protocol, not a bit.** Writing FM takes the VDP side away from the other CPU immediately, even mid-access, so both sides must agree who holds it and for how long. A design in the Aerobiz Ultimate project that flipped FM within microseconds of an answer passed 113 of 114 tests in PicoDrive and crashed Ares with wild SH-2 writes; the fix was an explicit grant-and-acknowledge pair on both sides. The same project raises a "busy" flag so its V-blank code leaves FM alone during long transfers, and the Virtua Racing Deluxe project switches FM only in V-blank <span class="tag emulator">emulator</span> [AU-NOTES, KNOWN_ISSUES, ROADMAP; VRD-NOTES, KNOWN_ISSUES, rendering notes].

**The frame buffer can even be the mailbox.** With the 32X layer blanked, frame buffer memory past the line table and 224 lines is unused, and it is the only memory both the 68000 and the SH-2s can reach. The Aerobiz Ultimate project writes decompressor output there in words and has the 68000 copy it out. Each word read costs the 68000 6-8 of its own clocks (2-4 waits on its 4-clock bus cycle), which the project puts at 2-3% of what the decompression would cost the 68000 — with care for the pages the FS flip swaps and the region a live layer would collide with <span class="tag emulator">emulator</span> [AU-NOTES, ROADMAP; 32X-HWM §4.4 p.77].

**Polling is traffic.** A CPU spinning on a register is not idle — every read is a bus cycle, and MK2's back-to-back COMM polling above shows the shape. Sega forbids `SLEEP` on the 32X SH-2s ([What Sega forbids or reserves](../sh2/overview.md#what-sega-forbids-or-reserves)), and no shipped game in the sources uses it. The cheaper shapes they use instead: poll with a delay between reads (Chaotix's Slave reads its command byte once every 99 passes of a delay loop), or park in a loop so small it caches (Motocross Championship's Slave, in ROM). Better still, let commands arrive by CMD interrupt, as After Burner Complete's Slave does, and spin only on on-chip state. If a poll cannot be avoided, put something useful between the reads.

## What emulators do not show

Contention itself is thinly modelled. PicoDrive implements neither the SH-2 cache nor SDRAM latency. Ares models the cache and charges one fixed cost per access, but none of the manual's ranges, no contention between the SH-2s and no 68000 stall on cartridge reads <span class="tag emulator">emulator</span> [AU-NOTES, hardware tests; PICODRIVE; ARES]. Everything tagged <span class="tag emulator">emulator</span> on this page was measured that way. A placement change can be invisible in one emulator and decisive on hardware; measure with the [profiling page](../howto/profiling.md), and keep the hardware list of what only the console can answer.

## What to take away

- Decide where each thing lives *once, deliberately*: code that must be fast in SDRAM, immutable data in ROM, streamed data through cache-through, pixels that are read back built in SDRAM and copied once ([the placement table](../32x/timing.md#where-things-should-live)).
- One bulk transfer beats continuous trickling, and the VDP's fill and the DMA channels are other people's bus cycles you do not have to spend.
- Two working SH-2s get along by staying in their caches and on-chip RAM, and sharing one double-buffered thing a frame.
- Every shared thing needs a named owner: the FM bit, the FIFO, the communication words, the frame buffer, and RV.
- Waiting is a cost you can move. Overlap it, sleep through it, or at least do not make it three CPUs' worth.
- Trust emulator timings for what a program executes, not for what it waits on.
