# Living with bus contention

Four processors (the 68000, the Z80 and the two SH-2s) and two video chips (the Mega Drive VDP and the 32X VDP) share the machine's memories, and none of them waits politely. When a 68000 access to the cartridge is slow, it is usually slow because an SH-2 got there first; when an SH-2 access to the palette stalls, it is because the 32X VDP is reading that palette to make the picture. A program can be slowed down by what the *other* processors are doing, not by anything it is doing itself. The prices of every access are in [Access timing per CPU](../32x/timing.md#the-figures); this page is about what real programs did with those prices. The short version: on a machine this crowded, where code and data live *is* the optimisation.

Most of the page is about the 68000 and the two SH-2s, the three CPUs that [Splitting work across three CPUs](cpu-split.md) also counts. The Z80 keeps to its own RAM and appears only in [the Mega Drive side](#the-mega-drive-side).

Every figure here is counted in the clocks of the CPU that pays it. Unmarked figures are SH-2 clocks (23.01 MHz on NTSC machines); 68000 clocks (7.67 MHz) are marked as such, and each one lasts three times as long ([timing](../32x/timing.md#the-figures)).

Four fights cover most of it:

1. **The 68000 against the SH-2s, over the cartridge.** Both sides run code and read data from the same ROM. When they collide the SH-2 wins and the 68000 waits [32X-HWM §4.1 p.74].
2. **The two SH-2s, over one bus.** SDRAM, the frame buffer, the cartridge and the registers all sit on one external bus, so a Slave access waits while the Master is using it, and the other way round [SH7604 §7.10; [Two SH-2s, one bus](../sh2/bsc.md#two-sh-2s-one-bus)].
3. **Everyone against the VDP, over the frame buffer and palette.** The CPUs work on the buffer that is not on screen, and swap at vertical blank. The palette is the part they really share: the VDP reads it every line, and a CPU access that collides waits up to a whole line. An auto fill also keeps the back buffer busy for the fill's whole length [32X-HWM §3.3; §4.4 p.77] ([below](#the-vdp-and-the-frame-buffer)).
4. **On the Mega Drive side, the 68000 against the Z80 and the Mega Drive VDP's DMA.** An older fight with older rules, but in 32X mode it runs into the first one: a DMA from the cartridge needs RV, and RV shuts the SH-2s out of the cartridge ([below](#the-mega-drive-side)).

The examples carry different weight. Motocross Championship, Knuckles' Chaotix, Mortal Kombat II, Star Wars Arcade and After Burner Complete are commercial releases, read from clean retail dumps: what they do ran on consoles, though not always well. The ECCO CinePak demo and the Runlength Mode Test are Sega sample programs from development cartridges that were never sold. d32xr, an open-source Doom port, and the S32X-SKILL notes are homebrew; d32xr's commit history records fixes made on consoles, while the skill's notes were tested mostly in PicoDrive. The Virtua Racing Deluxe project and the Aerobiz Ultimate project are the author's work in progress and have not yet run on a 32X, so what they report is tagged <span class="tag emulator">emulator</span>. Where this page says what Virtua Racing Deluxe itself does, that is the project's account of the game, from a ROM copy the project has patched ([VRD-NOTES](../appendices/bibliography.md#vrd-notes)).

## What each program did

The clearest way to see the tactics is what each program chose to put where.

**d32xr keeps the 68000 out of the cartridge.** Its 68000 main loop is copied into work RAM at startup, with a build note that it has to live there to stop the two SH-2s contending with it for the ROM [D32XR, main.c, crt0.s]. The SH-2s own the cartridge, and even then the game does not read textures from it while drawing: a texture cache copies the most visible textures into SDRAM a few per picture, nearest surfaces first, and swaps each texture's data pointer to the RAM copy so the drawing code never knows which copy it holds. Evicted entries get their ROM pointer back [D32XR, r_cache.c, r_phase9.c]. Levels larger than the directly mapped ROM window are paged through 512 KB cartridge bank windows, re-selecting the page on entry to the code that walks each structure [D32XR, marsnew.c, p_setup.c]. This is also the standard shape for multi-megabyte games on a 256 KB machine: immutable data — decoded graphics, palettes, music, levels — stays in ROM and is read in place at `0x02000000`, where it is cacheable and read-only; only mutable state goes to SDRAM [S32X-SKILL, architecture].

**Motocross Championship runs the other way, from ROM, and pays for it.** Both of its SH-2 programs execute in place from the cached cartridge window instead of being copied to SDRAM [MCX, user header and entry points]. It works because the cache absorbs the hot loops — even the Slave, parked in a two-instruction loop in ROM all game long, only fetches that loop from the cartridge once before the cache holds it. But every cold path pays cartridge misses (a cache line from ROM costs up to 136 SH-2 clocks against 12 from SDRAM, see [timing](../32x/timing.md#the-figures)), and it competes with the 68000, which is also running from the cartridge. The rest of the game is textbook placement: the Master renders into an SDRAM staging buffer and then makes one bulk transfer of about 64 KB to the cache-through frame buffer for each picture, instead of writing pixels to the frame buffer as it draws [MCX, headless runs].

**The ECCO CinePak demo streams through the cache-through window on purpose.** Its movie is read directly from the cartridge at the *cache-through* address (`0x22020000`), so megabytes of sequential frame data flow through the SH-2 without ever evicting code from the cache [ECCO, decoder entry]. It is not free: the decoder reads the stream a byte at a time, so every byte is a whole cartridge access, about twice the bus time the cached view would cost per byte. What it buys is a cache that keeps the decoder's code and tables ([Cache discipline](cache.md#what-a-read-costs-through-each-view)). Decoded frames are built in SDRAM and copied to the frame buffer one longword at a time, with five `nop`s after each store [ECCO, blit routine at `0x06000238`]. Each longword store is two word writes back to back, so no idle clock can ever fall between the halves: the `nop`s only come before the first half of the next longword, and the second half is always a back-to-back write. They are idle clocks, not work, and by the manual's rule (below) idle clocks can at best pay for themselves: each one takes at most one clock off the next write, and none once the write is down to its 3-clock floor. The loop's own load, pointer step, counter and branch already sit between the stores. On the manual's figures the `nop`s cost five clocks per longword and gain nothing back; what Sega meant them for is not recorded. And with the Slave parked, the demo never has two SH-2s fighting over the bus at all.

**The Runlength test attacks the frame buffer itself.** Its polygon renderer writes the display data in the VDP's run-length mode: one word per run of same-colour pixels, which the VDP expands while scanning out ([the VDP chapter](../32x/vdp.md#run-length)). A flat-shaded object's frame buffer traffic shrinks by whatever the average run length is, and the whole engine and its tables live in SDRAM [RLT, renderer]. This is the most literal answer to "the frame buffer is slow": write less of it.

**Knuckles' Chaotix lets the hardware do the clears.** Blanketing a frame buffer with a solid colour costs tens of thousands of bus cycles if a CPU writes every word, but the VDP's own fill does it in 7 + 3 × length SH-2 clocks while the CPU works elsewhere ([auto fill](../32x/vdp.md#auto-fill)). Both Chaotix and Motocross Championship blank their buffers that way at boot, two buffers each with the page bit toggled between [MCX, 68000 boot; CHAOTIX, headless runs]. During play, Chaotix's Master hands each picture's clear to its Slave: it writes a command byte, and the Slave issues 216 auto fills, one per line, waiting for each to finish, while the Master gets on with its own work. Between commands the Slave polls that byte with a 99-pass delay loop between reads, so its poll costs one register read every few hundred clocks instead of one every few [CHAOTIX, SH-2 code at `0x060002D4`-`0x060002FC`, `0x0600032C`-`0x0600035E`, `0x06004B12`, `0x06004B9A`].

**Mortal Kombat II shows the bill for doing it badly.** Its Master starts each 256-word auto fill and then polls the FEN bit until the fill finishes, 161 times a frame (together exactly the 224 rows of its 368-byte lines). By the manual's fill formula that is 161 × (7 + 3 × 256) = 124,775 clocks of waiting <span class="tag manual">manual</span> [32X-HWM §3.3, FILL function]. That figure is the formula's, not a measurement. The Master has about 384,000 clocks in an NTSC frame (23.01 MHz ÷ 59.92 frames a second; see [System architecture](../megadrive/architecture.md) for the refresh rate), so the clear spends about a third of its frame polling. Nothing sits between starting a fill and polling for it, and there was work to put there: the sprite routine that runs later in the same frame begins by collecting its active sprite records into a list and sorting it, all in SDRAM and touching no frame buffer address, before it draws the first one. The Slave, which only plays sound, could also have issued the fills, as Chaotix's does. Elsewhere in the game, the Slave's main loop reads a communication register back to back with no delay, taking bus cycles the Master wants for SDRAM, and the Master's command handler busy-waits through 67 port handshakes to receive one state block [MK2, `0x060010DC`, `0x060022B0`, `0x06002C00`, `0x06005178`, `0x060003F4`]. None of it is wrong; all of it is bus time somebody else wanted.

## Moving data without paying twice

- **Batch and align frame buffer writes.** Every access to the frame buffer is a bus transaction, and the bus is 16 bits wide, so a longword store goes out as two word writes back to back <span class="tag manual">manual</span> [SH7604 §7.3.1; [Bus state controller](../sh2/bsc.md#what-a-16-bit-bus-costs); [Writing from the SH-2](../32x/vdp.md#writing-from-the-sh-2)]. S32X-SKILL's advice is to pack four 8-bit pixels into one aligned longword and unroll the store loop, keeping tiles on 4-pixel boundaries so a 16-pixel tile row is exactly four aligned stores <span class="tag emulator">emulator</span> [S32X-SKILL, optimization notes]. That does beat four byte stores, which are four transactions for four pixels, against two for the longword. On the bus it is no better than two word stores, though; what it saves is instructions. An SH-2 frame buffer write goes through a small write buffer: 3 clocks while it has room, 5 when it is full. The 5 assumes writes back to back, as the two halves of a longword always are; each idle clock before a write takes one clock off it, but never below 3 <span class="tag manual">manual</span> [32X-HWM §4.4 p.77]. So an empty gap only buys back what it costs. What wins is putting work the loop needs anyway (the next pixel's arithmetic, the pointer updates) between the stores, so that the buffer drains while the CPU is busy rather than idle. How deep the buffer is remains <span class="tag disputed">disputed</span> ([discrepancy 4](../appendices/discrepancies.md)).
- **Let DMA carry the big copies.** Frame buffer fills and sample streaming through the SH-2's DMA run without the CPU, and the CPU can compute while they move [S32X-SKILL, optimization notes; [DMA controller](../sh2/dmac.md)]. For 68000-to-SH-2 bulk data the [DREQ FIFO](../32x/fifo.md) is the intended path.
- **Treat RV as a shutdown, not a tool.** RV hands the cartridge back to the Mega Drive VDP for DMA, and while it is 1 any SH-2 access to the cartridge stalls until the 68000 clears it [32X-HWM §4.1 p.74]. d32xr's header makes that a rule for both CPUs: no ROM reads while RV is set, whether from code, DMA or interrupt handlers [D32XR, marshw.h warning]. Interrupts are only at risk where the vector table or the handler is in the cartridge. A program the boot ROM copies to SDRAM normally keeps both there (Mortal Kombat II's vector tables are at `0x06000000` and `0x06000120`, Chaotix's at `0x06000000` and `0x06000080`), but Motocross Championship runs from the cartridge with both vector tables in ROM, so any interrupt it took during an RV window would stall too [MK2, vector tables; CHAOTIX, Slave entry and dispatch; MCX, user header and entry points]. The Aerobiz Ultimate project needs RV windows for Mega Drive DMA, so it keeps its SH-2 code in SDRAM, where the windows cost the SH-2s nothing as long as they do not touch `0x22000000` meanwhile [AU-NOTES, PORT_ARCHITECTURE]. The other way out is never to set RV. The Virtua Racing Deluxe project reports that the game does no DMA from the cartridge to VRAM, the transfer RV exists for, and that every write it makes to the DREQ control register sets only 68S, for FIFO transfers the 68000 feeds by hand, so the project's own SH-2 code can safely run from the cartridge [VRD-NOTES, KNOWN_ISSUES]. If you want the cartridge to yourself, the question is what everyone else will be executing meanwhile.

## Two SH-2s, both working

Parking the Slave in a loop its cache holds, as the ECCO demo does, ends the second fight by forfeit. When both SH-2s have real work, the programs read for this book keep each CPU on memory the other does not need:

- **Keep the hottest loop off the bus.** Cache hits and on-chip RAM never use the shared bus, so two SH-2s working from them do not slow each other at all ([Two SH-2s, one bus](../sh2/bsc.md#two-sh-2s-one-bus)). Star Wars Arcade's Slave cuts polygons into trapezoids in a routine it keeps in its 2 KB of on-chip RAM, and leaves the pixel writes to the VDP's auto fill, while the Master transforms the next picture [SWA, SH-2 code at `0x060008F0`; [Splitting work across three CPUs](cpu-split.md)].
- **Share little, once a picture.** Star Wars Arcade's Master writes polygon lists into one of two buffers while the Slave reads the other, and the Slave purges its cache once per picture, before reading each list, so that it reads the lists the Master just wrote and not copies its own cache kept from the picture before (the reason is in the next bullet) [SWA, SH-2 code at `0x06000E96`-`0x06000ECE`, `0x060007D0`]. After Burner Complete goes further: its Master draws, its Slave mixes sound, and the two share no SDRAM at all [AB32X, SH-2 program].
- **Read shared data once.** Each SH-2 has its own cache, and nothing tells it when the other CPU has written: a cached copy of shared data stays as it was until the line is refilled, so a cached read can return old data [SH7604 §8.5.2, §8.5.3; [Keeping the views in step](../sh2/cache.md#keeping-the-views-in-step)]. That is why the Slave above purges before each list. The two safe ways to read shared data both have a price. Reading through `0x26000000` always goes to memory, but it costs a full burst for each read, so read each item once and keep it in a register. Purging just the lines the other CPU wrote keeps later reads cheap, as d32xr mostly does ([the placement table](../32x/timing.md#where-things-should-live); [Cache discipline](cache.md)).
- **Do not run DMA on both at once.** If both SH-2s run DMA at the same time, one of them slows to a crawl until the other finishes <span class="tag manual">manual</span> [32X-HWM §5.3, DMA restrictions].

No source measures what the two SH-2s cost each other on a console, and no emulator models it (see [below](#what-emulators-do-not-show)). d32xr, where both CPUs draw walls from the same lists, is the open case ([Splitting work across three CPUs](cpu-split.md#open-questions)).

## The VDP and the frame buffer

The 32X VDP claims the frame buffer and the palette in three ways, and the programs read for this book answer each differently.

- **The picture.** The VDP reads the buffer FS shows and the CPUs get the other one, so a program never draws where the VDP is reading, and the swap is the handover. Where the sources show a flip, it is in vertical blank: ECCO's blit routine ends by waiting for VBLK in the frame buffer control register and then inverting FS, Mortal Kombat II waits for the V interrupt and inverts FS, and the Virtua Racing Deluxe project flips from its 68000's V-blank handler [ECCO, SH-2 code at `0x06000254`-`0x06000264`; MK2, `0x06001088`, `0x060010A4`; VRD-NOTES, rendering pipeline] ([Frame buffers and the FS bit](../32x/vdp.md#frame-buffers-and-the-fs-bit)). What sharing with the VDP costs a CPU working on the other buffer is inside the manual's frame buffer ranges (reads 5-12 waits, writes 1-3); no source splits them by cause or measures them on a console [32X-HWM §4.4 p.77].
- **The palette.** There is only one, and the VDP reads it every line while it draws. A CPU access that collides waits until the end of the line, up to 64 µs, and PEN reads 1 when it is free <span class="tag manual">manual</span> [32X-HWM §4.4 p.77; §3.2.3] ([Colours and the palette](../32x/vdp.md#colours-and-the-palette)). Mortal Kombat II avoids the wait by writing all 256 entries straight after the V-interrupt wait, without testing PEN [MK2, `0x06000982`]. The Aerobiz Ultimate project cannot always pick its moment, because it copies the Mega Drive's palette writes at the moment the game makes them, so it waits for PEN before each word <span class="tag emulator">emulator</span> [AU-NOTES, ROADMAP U-090; [Following the Mega Drive's palette](../32x/compositing.md#following-the-mega-drives-palette)].
- **Auto fill.** For the fill's whole 7 + 3 × length clocks the back buffer belongs to the VDP, and FEN reads 1. The programs above and in the VDP chapter show three ways out: poll, as Mortal Kombat II does; give the polling to the other SH-2, as Chaotix does; or time the fill and carry on, as Star Wars Arcade does with its watchdog interrupt ([Auto fill](../32x/vdp.md#auto-fill)).
- **Refresh.** FEN also reads 1 for 40 clocks during each DRAM refresh, but the manual says the DRAM can still be accessed then <span class="tag manual">manual</span> [32X-HWM §3.3, register latch timing]. Refresh does not shut the buffer. It can only make a poll for the end of a fill read 1 for up to 40 clocks longer.

Ares holds the SH-2 off the palette while the VDP has it, and drops frame buffer accesses made during a fill, but neither emulator charges the VDP's reads or the refresh against the frame buffer ([timing](../32x/timing.md#in-emulators)). Only a console can say what they cost in practice.

## The Mega Drive side

The 68000's older fights still happen in 32X mode, and two of them reach the 32X side. The full rules are in [Z80 bus control](../megadrive/z80.md) and [DMA](../megadrive/vdp-dma.md).

- **DMA from the cartridge needs RV.** In 32X mode the Mega Drive VDP can only DMA from the cartridge with RV = 1, which stalls the SH-2s' cartridge accesses (above) and removes the `$880000` window the 68000's own code normally runs from [32X-HWM §3.1 pp.13-14; [The RV bit](../32x/architecture.md#the-rv-bit)]. So the code that starts the DMA runs from work RAM, the SH-2s keep to SDRAM for the duration, and since the transfer stops the 68000 until it ends, big ones belong in vertical blank ([What the VDP and DMA do to real speed](../megadrive/m68k.md#what-the-vdp-and-dma-do-to-real-speed); [How much fits in a frame](../megadrive/vdp-dma.md#how-much-fits-in-a-frame)). A DMA from work RAM does not need RV at all.
- **The Z80 borrows the 68000's bus.** Every Z80 access through its bank window is a 68000 bus cycle that holds the 68000 off, and the manual applies the cartridge competition with the SH-2s to the Z80 as well [32X-HWM §4.3 p.76; [timing](../32x/timing.md#the-z80)]. Keep the Z80 working from its own RAM. d32xr's 68000 unpacks the music into work RAM and, holding the Z80's bus, copies it into Z80 RAM in 512-byte blocks; the Z80 then plays the music's commands from its own memory [D32XR, src-md/vgm.c; src-md/crt0.s `bump_fm`; src-md/z80_vgm.s80]. Z80 *writes* to the 32X are a separate hazard ([The Z80's view](../32x/architecture.md#the-z80s-view)).

## Sharing without colliding

The memory map leaves only three channels that carry data between the 68000 and the SH-2s: the 16 communication bytes, the DREQ FIFO (68000 to SH-2 only), and the frame buffer DRAM under the FM arbitration bit. FM hands the VDP registers and the palette over along with the frame buffer, so they count as one channel [32X-HWM §3.2.1 p.19; [Who can reach what](../32x/architecture.md#who-can-reach-what)]. A fourth path, the CMD interrupt that the 68000 raises to get an SH-2's attention, carries only a signal: it says that something is waiting in one of the three. The SH-2 cannot see 68000 work RAM at any address, and the 68000 cannot see SDRAM [32X-HWM; VRD-NOTES, communication analysis]. (The two SH-2s share far more: all of SDRAM, which is the second fight.) The Virtua Racing Deluxe project lost three attempts to a work-RAM ring buffer before reading that page of the manual [VRD-NOTES, KNOWN_ISSUES]. Designing a structure shared between the 68000 and the SH-2s outside those three channels is not creative, it is broken.

**Frame buffer ownership is a protocol, not a bit.** Writing FM takes the VDP side away from the other CPU immediately, even mid-access, so both sides must agree who holds it and for how long. A design in the Aerobiz Ultimate project that flipped FM within microseconds of an answer passed 113 of 114 tests in PicoDrive and crashed Ares with wild SH-2 writes; the fix was an explicit grant-and-acknowledge pair on both sides. The same project raises a "busy" flag so its V-blank code leaves FM alone during long transfers, and the Virtua Racing Deluxe project switches FM only in V-blank <span class="tag emulator">emulator</span> [AU-NOTES, KNOWN_ISSUES, ROADMAP; VRD-NOTES, KNOWN_ISSUES, rendering notes].

**The frame buffer can even be the mailbox.** Frame buffer memory past the picture's line table and lines is unused, and it is the only memory both the 68000 and the SH-2s can reach. The Aerobiz Ultimate project puts a mailbox at offset `$12000`, just past a 256-word line table and 224 lines of 320 pixels, which end at `$11A00`. The SH-2 writes decompressor output there in words and the 68000 copies it out. The technique needs no particular state of the layer, only memory the picture does not show. The shipping build in fact leaves the layer blanked, and the project's roadmap notes that a live layer using more of the buffer would collide with the mailbox and force it to move or be interlocked <span class="tag emulator">emulator</span> [AU-NOTES, ROADMAP; disasm/modules/shared/definitions_32x.asm].

Every transfer is an FM handoff, the protocol of the paragraph above. The project reads the manual as making a handoff a stall for both CPUs until the grant arrives, so it moves data in batches, not block by block. Each trip is also kept inside one FS state, in chunks of `$800` words, because a flip between the two sides' accesses would leave them looking at different pages <span class="tag emulator">emulator</span> [AU-NOTES, ROADMAP; PORT_ARCHITECTURE].

Each word the 68000 reads costs it 6-8 of its own clocks (2-4 waits on its 4-clock bus cycle) [32X-HWM §4.4 p.77]. The project puts the whole transport at 2-3% of what the decompression itself would cost the 68000 <span class="tag emulator">emulator</span> [AU-NOTES, ROADMAP].

**Polling is traffic.** A CPU spinning on a register is not idle — every read is a bus cycle, and MK2's back-to-back COMM polling above shows the shape. Sega forbids `SLEEP` on the 32X SH-2s ([What Sega forbids or reserves](../sh2/overview.md#what-sega-forbids-or-reserves)), and no shipped game in the sources uses it. The cheaper shapes they use instead: poll with a delay between reads (Chaotix's Slave reads its command byte once every 99 passes of a delay loop), or park in a loop so small it caches (Motocross Championship's Slave, in ROM). Better still, let commands arrive by CMD interrupt, as After Burner Complete's Slave does, and spin only on on-chip state. If a poll cannot be avoided, put something useful between the reads.

## What emulators do not show

Contention itself is thinly modelled. PicoDrive implements neither the SH-2 cache nor SDRAM latency. Ares models the cache and charges one fixed cost per access, but none of the manual's ranges, no contention between the SH-2s and no 68000 stall on cartridge reads <span class="tag emulator">emulator</span> [AU-NOTES, hardware tests; PICODRIVE; ARES]. Everything tagged <span class="tag emulator">emulator</span> on this page was measured that way. A placement change can be invisible in one emulator and decisive on hardware; measure with the [profiling page](../howto/profiling.md), and keep a list of what only the console can answer ([Testing on real hardware](../howto/real-hardware.md#the-checklist) has one to start from).

## What to take away

- Decide where each thing lives *once, deliberately*: code that must be fast in SDRAM, immutable data in ROM, streamed data through cache-through, pixels that are read back built in SDRAM and copied once ([the placement table](../32x/timing.md#where-things-should-live)).
- One bulk transfer beats continuous trickling, and the VDP's fill and the DMA channels are other people's bus cycles you do not have to spend.
- Two working SH-2s get along by staying in their caches and on-chip RAM, and sharing one double-buffered thing per picture.
- Every shared thing needs a named owner: the FM bit, the FIFO, the communication words, the frame buffer, and RV.
- Waiting is a cost you can move. Overlap it with other work, and where you cannot, spin on on-chip state that an interrupt handler sets, not on a register that costs a bus cycle every time you look at it. (On the SH-2s Sega forbids `SLEEP`, so waiting means spinning.)
- Trust emulator timings for what a program executes, not for what it waits on.
