# Z80 bus control

The Z80 owns sound RAM, the YM2612 registers and its bank window. Whenever the 68000 wants any of them, it stops the Z80 first, through two control registers, and puts it back afterwards. Done right, that is a few microseconds of borrowed time; done wrong, it is corrupted sound RAM and wrong data from the cartridge. This page covers the two registers, the request sequence and its traps, loading a Z80 program at start-up, the bank window from the Z80's side, and the Z80's one interrupt. What lives where is in [System architecture](architecture.md#the-z80-memory-map); the sound-side rules are in [The Z80 and sound](sound.md#the-rules).

## The two registers

Both sit on bit 8 of a word, like the rest of the `$A1xxxx` control area [MD-SWM §4.4]:

| Address | Write | Read |
|---------|-------|------|
| `$A11100` | `$0100` request the bus, `$0000` release | Bit 8 (bit 0 of a byte read): 0 = Z80 stopped, bus usable; 1 = Z80 running |
| `$A11200` | `$0100` let the Z80 run, `$0000` hold it in reset | — |

The meaning of the status bit was long unclear because the sound manual bound into MD-SWM describes it the other way round; shipped code settles it: Aerobiz Supersonic and d32xr both wait for the bit to read 0 ([discrepancy 15](../appendices/discrepancies.md)) [AB-DISASM, Z80_RequestBus.asm; D32XR, src-md/crt0.s].

Sega's procedure writes and reads with word access; byte access works too, and the status is then bit 0 [MD-SWM §4.4]. Everything **inside** the Z80 area — sound RAM, the YM2612, the bank register — is byte access only [MD-SWM §4.5].

## Taking the bus

The whole exchange [MD-SWM §4.4]:

```asm
; a4 = $A11100
TakeZ80Bus:
    move.w  #$0100,(a4)      ; request
.wait:
    btst    #0,(a4)          ; byte read of the same address
    bne.s   .wait            ; 0 = granted
    rts
GiveZ80Bus:
    move.w  #$0000,(a4)
    rts
```

Three facts give the shape of the code:

- **The grant is not instant.** The Z80 finishes what it is doing first; that is why the bit is polled. Sega's own procedure and every shipped routine loop on it [MD-SWM §4.4; AB-DISASM, Z80_RequestBus.asm `$2662`].
- **Once the bit reads 0, the bus is free.** The Z80 finishes its current machine cycle, floats its address, data and control lines, and only then signals the grant [Z80-UM pp.6, 11]. No wait is needed after the grant. Every shipped routine read for this book touches sound RAM in the very next instruction: Aerobiz Supersonic, Star Wars Arcade, Mortal Kombat II, After Burner Complete, Knuckles' Chaotix and Motocross Championship [AB-DISASM, Z80_SoundInit.asm; SWA, 68000 code at `$EF42`; MK2, `$40824`; AB32X, `$1A66E`; CHAOTIX, `$4E80`; MCX, `$255C0`]. Exodus also reads the bit straight from the grant line, with no delay [EXODUS, MDBusArbiter.cpp].
- **The Z80 stops dead, not just its bus.** Its "CPU function" stops until the bus returns [MD-SWM §4.4], so a held Z80 plays no samples and services no interrupt. Keep each hold short.
- **Requests do not nest.** If an interrupt handler requests and releases the bus while the main program already holds it, the main program ends up writing sound RAM with the Z80 running again — Sega's bulletin lists damaged Z80 RAM and wrong bank-window reads as the result. Disable interrupts around every bus request <span class="tag manual">manual</span> [MD-TB #7; MD-SDM §5.5].

Aerobiz avoids the nesting problem in its callers instead: a flag at `$C70(a5)` says "the caller already holds the bus", so its DMA and input routines skip their own request when called from a path that holds it [AB-DISASM, ConfigVDPDMA.asm, InitInputArrays.asm].

### When Sega says to hold it

Two rules name the moments a request is compulsory:

- **Around every DMA from 68000 memory to the VDP.** During such a DMA the VDP owns the 68000's bus, and a Z80 access through the bank window at that moment is unsafe [MD-TB, addendum 4 §1]. See [DMA](vdp-dma.md#three-rules-when-the-source-is-rom-or-ram).
- **Around every access to `$A100xx`.** If the 68000 touches that range — the controller ports — in the bus cycle immediately before the Z80 enters the main bus, the Z80's cycle can come up too short to carry its data, and the read or write is wrong <span class="tag manual">manual</span> [MD-SDM §5 S1]. The cure is the sequence above around the port access; Aerobiz parks the Z80 for its whole pad read for this reason [AB-DISASM, InitInputArrays.asm]. Synchronising port access to the vertical interrupt, far from any window traffic, also avoids the bad timing [MD-SDM §5 S1].

The YM2612 needs the bus as well, plus its own timing care: the busy flag is read at `$4000` (68000 `$A04000`) and nowhere else [MD-TB #11; MD-SDM §5.5]. That story is in [The Z80 and sound](sound.md#the-rules).

## Loading a program

At power-on the Z80 is held in reset, so the 68000 can fill sound RAM before it runs [MD-SWM §4.4]. The safe order, mask interrupts first as always:

1. Mask interrupts on the 68000.
2. Request the bus and poll for the grant.
3. Copy the program into sound RAM at `$A00000`, one byte at a time.
4. Write `$0000` to `$A11200` (hold the Z80 in reset), release the bus, then write `$0100` to `$A11200`. The Z80 starts from address `$0000` with the new program.

Aerobiz's start-up routine does exactly this, with two details worth stealing [AB-DISASM, Z80_SoundInit.asm `$260A`]:

- The driver size comes from two PC-relative labels (end − start), and the copy loop's `dbra` uses that byte count directly, so it copies one byte more than the driver — harmless, as it lands in unused RAM.
- Restarting the Z80 also resets the YM2612 [MD-SWM, sound software manual §II.1], so a driver that loads itself this way configures the chip from scratch afterwards.

A program can also be reloaded at any time the sound is allowed to stop: hold reset, take the bus, overwrite, restart. The 68000 must not, at any point, try to run code or stack through the Z80 area — nothing of the 68000's lives there.

## The bank window from the Z80 side

The Z80's `$8000-$FFFF` is a 32 KB window onto the 68000's 16 MB, and the bank register at Z80 `$6000` chooses which 32 KB [MD-SWM §4.5]. A sound driver points it at sample data in the cartridge and streams bytes through it. The mapping and its cost in 68000 cycles are described in [System architecture](architecture.md#the-bank-window); the rules for the driver writer are:

- **Only the Z80 writes the bank register**, and the 68000 must not touch the window from its side (`$A08000` up is simply not mapped for it) [MD-SWM §4.5].
- **The register takes nine single-bit writes**, each using bit 0 of a byte written to `$6000`. The nine bits become 68000 address bits A15-A23 of the window start [MD-SWM §4.5].
- **Write A15 first and A23 last.** The register is a shift register: each write enters at the A23 end and pushes the earlier bits down, so the first of the nine writes ends up as A15. MD-SWM's table pairs write 1 with A23 instead (the scan agrees with the transcription, so the slip is Sega's), but shipped drivers settle the order [MD-SWM §4.5; [discrepancy 35](../appendices/discrepancies.md)]:
  - **Aerobiz Supersonic's** driver takes the high byte of a 68000 address (A23-A16) in A and A15 in the carry. It writes the carry first, then the bits of A from bit 0 to bit 7, and maps the address's low 15 bits into `$8000-$FFFF` [AB-DISASM, Z80 code at `$05BF`, called from `$041A`; the driver is copied from cartridge `$2696`].
  - **Knuckles' Chaotix's** driver writes bits 0-5 of a bank number, lowest first, then 0, 0 and 1. With the first write as A15, consecutive bank numbers are consecutive 32 KB blocks from `$800000`, the cartridge's place in the 68000's map in 32X mode. Read the other way round, the constant 1 would land on A15, and the bank number would move in 256 KB steps [CHAOTIX, Z80 code at `$0088`; the driver is copied from cartridge `$075B6A`].
  - Genesis Plus GX, BlastEm and PicoDrive all shift each write in at A23 [GPGX, core/genesis.c; BLASTEM, genesis.c; PICODRIVE, pico/memory.c].

On a 32X there is one more window rule: whenever the Z80 writes the PSG, its bank register must point outside the cartridge areas, or the 32X can corrupt its own registers (see [The Z80 and sound](sound.md#the-rules)) [32X-TI item 22].

## Interrupts on the Z80 side

The Z80 receives exactly one interrupt source: vertical blank, about every 16 ms (NTSC), asserted for about 64 µs [MD-SWM, sound software manual §I.2]. Exodus and Genesis Plus GX raise it at the same moment as the 68000's vertical interrupt, even when that interrupt is disabled in register 1, and drop it when the line counter next changes: 2,632 master clocks later, about 49 µs or 175 Z80 cycles. PicoDrive holds it for one line <span class="tag emulator">emulator</span> [EXODUS, S315-5313_Ports.cpp; GPGX, core/system.c; PICODRIVE, pico/pico_cmn.c]. A driver that needs a finer rhythm counts cycles or polls the YM2612's timers, which do not interrupt at all [MD-SWM, FM sound source overview].

In interrupt mode 1 the Z80 jumps to the fixed address `$38`; a driver puts its frame tick there and does its sequencing in it. Knuckles' Chaotix's driver is built this way: `di`, `im 1`, and its tick at `$38` [CHAOTIX, Z80 code at `$0000`, `$0038`].

**An interrupt that arrives during a bus hold is not stored.** The Z80 looks at its interrupt line only at the end of an instruction, and it does not accept the interrupt while a bus request is active [Z80-UM pp.6, 12] <span class="tag manual">manual</span>. The line is a level, not a latched event, so what happens depends on how long the hold lasts:

- **The 68000 releases the bus while the line is still asserted.** The Z80 takes the interrupt at the end of its next instruction, late but not lost. PicoDrive keeps the line asserted through a hold for this reason; its comment names *Teddy Blues* as a game that needs it [PICODRIVE, pico/pico_cmn.c].
- **The hold lasts past the end of the pulse.** The Z80 never sees that frame's interrupt, and the driver misses a tick.

The vertical interrupt is exactly when the 68000 is most likely to hold the bus, because Sega's rules require the hold around every DMA from 68000 memory ([above](#when-sega-says-to-hold-it)). A handler that takes the bus at the top and runs a vertical-blank DMA of several lines will swallow the Z80's interrupt every frame. A driver that keeps time from the interrupt then runs slow. Either release the bus within about 40 µs of the vertical interrupt (about 300 68000 cycles), or let the 68000 do its DMA first and only then post work for the Z80, or have the driver keep time with a YM2612 timer instead.

## In a shipped game

Aerobiz is the worked example throughout, because its input and DMA paths request the bus by rule rather than by exception [AB-DISASM]:

- **One place owns the request.** Two tiny routines — request-and-wait and release — are the only code that touches `$A11100`; every caller goes through them or through the already-holding flag.
- **The bus is released before the Z80 works.** Sending a sound command means writing a mailbox into sound RAM, releasing, and polling until the Z80 clears the busy byte — the 68000 never holds the bus across the Z80's own work [AB-DISASM, CmdSendZ80Param.asm]. The protocol is described in [The Z80 and sound](sound.md#aerobiz-supersonic-everything-on-the-z80).

## Open questions

- How long is the Z80's interrupt held on a console: about 49 µs to the next line change (Exodus, Genesis Plus GX), a full line (PicoDrive), or the 64 µs MD-SWM gives? A Z80 program that counts cycles from a bus release would measure the last moment a release still lets the interrupt through.
- Does the Z80 get its interrupt when the 68000's vertical interrupt is disabled (IE0 = 0)? The emulators say yes; Exodus marks it as not yet confirmed.
